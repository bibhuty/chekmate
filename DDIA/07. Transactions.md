# Transactions: The Slippery Concept

* **The Purpose:** A transaction is a way for an application to group several reads and writes together into a single logical unit. 
* **The Benefit:** By using transactions, the application is free to ignore certain potential error scenarios and concurrency issues because the database takes care of them instead (these are called **safety guarantees**).
* **The Debate:** With the rise of NoSQL, two exaggerated viewpoints emerged: that transactions are the "antithesis of scalability" and that they are an "essential requirement for serious applications." The truth is simply that they are a technical design choice with trade-offs.

# The Meaning of ACID (And Its Misconceptions)
One database’s implementation of ACID does not equal another’s implementation. It has largely become a marketing term.
* **Atomicity (Abortability):** Atomicity is *not* about concurrency (that is Isolation). It describes what happens if a client wants to make several writes, but a fault occurs halfway through. 
    * *The Guarantee:* The defining feature of ACID atomicity is **abortability**—the ability to abort a transaction on error and have all writes from that transaction safely discarded. 
* **Consistency (Application Logic):** Consistency refers to an application-specific notion of the database being in a "good state" (e.g., account balances must balance). 
    * *The Catch:* A, I, and D are properties of the database. Consistency is a property of the *application*. The database only stores what you tell it to; it cannot magically enforce your business logic. 
* **Isolation (Concurrency Control):** Concurrently running transactions shouldn't interfere with each other. 
    * *The Ideal:* Classic textbooks formalize this as **Serializability**—the database ensures that if transactions run concurrently, the final result is the exact same as if they had run sequentially (one after another).
    * *The Reality:* Because true serializable isolation carries a massive performance penalty, most popular databases implement weaker guarantees (like Snapshot Isolation).
    * *Point to ponder upon:*
	    * **Who decides the order if two transactions arrive concurrently?**
		    * The order is non-deterministic and entirely out of the application's hands. It is decided by microscopic race conditions at the database level (network jitter, OS thread scheduling, and which query hits the Lock Manager a nanosecond faster). 
		* **The Core Concept:** 
			* Strict *Serializable Isolation* does **not** guarantee a predictable, deterministic order (e.g., "A will always happen before B"). It only guarantees that the database will arbitrarily pick one to go first, and the final state will reflect *some* valid sequential execution. The application code must be prepared to handle whichever outcome occurs.
* **Durability:** The promise that once a transaction has committed successfully, any data it has written will not be forgotten, even in a hardware crash.
    * *The Reality Check:* Perfect durability does not exist. Disks fail, SSDs decay, and correlated power outages can wipe memory. Durability is achieved via risk-reduction techniques used *together* (writing to disk + replicating to remote machines + backups).

# Single-Object vs. Multi-Object Operations

* **Single-Object Writes:** Storage engines universally aim to provide atomicity and isolation on the level of a single object (like a JSON document or Key-Value pair). They use logs for crash recovery (Atomicity) and single-object locks for concurrent writes (Isolation). These are useful, but they are *not* multi-object transactions.
* **Grouping Multi-Object Operations:** To provide ACID across multiple objects, the database must know which operations belong to which transaction. 
    * *The Standard Way:* Relational databases group operations based on the client's TCP connection (everything between a `BEGIN TRANSACTION` and a `COMMIT` statement).
> **Unique Transaction Identifiers vs TCP connections for transaction**
> Imagine you buy an item on Amazon. Your app sends the `COMMIT` command over the TCP connection, and the database deducts the money. But before the database can send the "Success!" message back to you, your WiFi drops (TCP connection interrupted). 
> 
> Because you never got the success message, your app thinks it failed and retries the exact same purchase. If the database relies *only* on the TCP connection, it sees this as a brand new transaction and deducts your money twice. 
> 
> If the transaction is grouped by a **Unique Transaction Identifier (Idempotency Key)** instead (e.g., `Transaction_ID: 999`), when your app reconnects and retries, the database checks the ID and says, *"Wait, I already committed Transaction 999 successfully three seconds ago. I will ignore this retry and just send the 'Success' message again."* This prevents duplicate processing.

## The Need for Multi-Object Transactions
Many NoSQL datastores abandoned multi-object transactions because they are hard to implement across partitions. But we still need them for three core reasons:
1.  **Foreign Key References:** In relational models, inserting several records that refer to one another requires coordination to prevent broken links.
2.  **Denormalized Data:** In document databases (like MongoDB), when denormalized information needs to be updated, you must update several different documents in one go to prevent the data from going out of sync.
3.  **Secondary Indexes:** If you change a value, the secondary index must also be updated. Without transaction isolation, a record might appear in one index but not another.

## Handling Errors and Aborts (The Problem with Retries)
The whole point of ACID aborts is to enable safe retries. However, blindly retrying an aborted transaction is a flawed error-handling mechanism:
1.  **Duplicate Execution:** If the transaction succeeded but the network failed during the acknowledge step, a simple retry causes it to perform twice (unless you have an application-level deduplication mechanism).
2.  **Overload Feedback Loops:** If the error is due to the server being overloaded, retrying immediately makes the problem exponentially worse. (Fix: Limit max retries and use exponential backoff).
3.  **Permanent Errors:** Retrying a transient error (network blip) makes sense. Retrying a permanent error (constraint violation / invalid input) is useless.
4.  **External Side Effects:** If your transaction triggers an action outside the database (like sending an email), that email will be sent again every single time you retry the database transaction.
5. **Client Process Crashes:** If the database aborts a transaction, the uncommitted data is temporarily held in the application server's memory while it waits to retry. If the application server (the client) crashes during this waiting period, that uncommitted data is permanently lost. ACID Durability cannot protect data that hasn't successfully committed yet.

# Weak Isolation Levels
Concurrency bugs are notoriously hard to find because they only trigger under unlucky timing. Because strict *Serializable* isolation has a massive performance cost, many databases use weaker levels of isolation by default. 

**The Reality Check:** A popular myth is "Use an ACID database if handling financial data." This misses the point. Even popular relational databases (considered ACID) use weak isolation by default, meaning they won't automatically prevent all concurrency bugs.
## Read Committed
This is the most basic level of transaction isolation (and the default in Postgres, SQL Server, Oracle, etc.). It makes two specific guarantees:

1.  **No Dirty Reads:** When reading, you will only see data that has *already been committed*.
    * *Implementation:* For every object written, the database remembers both the old committed value and the new uncommitted value. While a transaction is ongoing, any other readers are simply given the old value. 
2.  **No Dirty Writes:** When writing, you will only overwrite data that has *already been committed*.
    * *Implementation:* Databases prevent dirty writes by using **row-level locks**. If two transactions want to write to the same row, the second one must wait for the first to commit or abort before it can acquire the lock.

**The Flaw:** Read Committed does *not* prevent the race condition between two counter increments (the Lost Update problem). 

## Snapshot Isolation and Repeatable Read
If you use Read Committed, you can still experience **Read Skew (Non-repeatable Read)**. 
* *Example:* Alice has $1000 split across two accounts ($500 each). A transaction transfers $100 from Account 1 to Account 2. If Alice views her balances at the exact wrong millisecond, she might see Account 1 at $500 (before the transfer) and Account 2 at $400 (after the transfer). It temporarily looks like she only has $900.
* While temporary read skew is acceptable for a user interface, it is intolerable for **Backups** (you'd back up a corrupted state) and **Analytic Queries** (scanning large parts of the DB would yield nonsensical results).
> **"What does Repeatable Read means?"**
> In the official SQL standard, "Repeatable Read" simply means: *If you read a row twice during the same transaction, you are guaranteed to see the exact same data both times (no one else can change it out from under you).* > 
> Nobody actually knows what it means in practice because the SQL standard is poorly written. PostgreSQL and MySQL call their Snapshot Isolation implementation "Repeatable Read" for marketing/compliance reasons, while Oracle calls it "Serializable."

**The Solution:** Snapshot Isolation .
The idea is that each transaction reads from a *consistent snapshot* of the database—meaning it sees all the data that was committed at the *exact moment the transaction started*. 

### Implementing Snapshot Isolation (MVCC)
From a performance perspective, the key principle of snapshot isolation is: **Readers never block writers, and writers never block readers.**
* To do this, the database must keep several different committed versions of an object side-by-side. This is known as **Multi-Version Concurrency Control (MVCC)**.
* *How it works (Postgres example):* Every transaction gets a unique, always-increasing ID (`txid`). When you delete a row, it isn't actually deleted; it is just marked with a `deleted_by` field containing your `txid`. A garbage collector cleans it up later.
* *Visibility Rules:* An object is visible to you only if the transaction that created it had already committed when *your* transaction started.
### Indexes and Snapshot Isolation
How do indexes work in a multi-version database if there are several versions of the same row? There are a few different architectural approaches:
1.  **Index to All Versions (The Standard Approach):** The secondary index simply points to *all* versions of an object. When a transaction queries the index, it must filter out any object versions that are not visible to it (based on its `txid`). When garbage collection removes the old row version, it also removes the corresponding index entry.
2.  **Page-Level Optimization (PostgreSQL HOT):**  If a database creates a new version of a row on a completely different disk page, all the secondary indexes must be updated to point to that new physical address, which is incredibly slow. Postgres uses an optimization called HOT (Heap-Only Tuples): if the new version of the row fits on the *exact same physical memory page* as the old one, the secondary index doesn't need to be updated at all!
3.  **Append-Only / Copy-on-Write B-Trees (CouchDB, Datomic, LMDB):** Instead of modifying existing pages or maintaining complex transaction IDs in the index, these databases use an append-only variant of a B-tree. 
    * *How it works:* They never overwrite pages. Instead, they create a *new copy* of each modified page. Parent pages are then updated to point to these new child pages. Any pages not affected by the write remain immutable.
    * *The Snapshot Benefit:* Every write transaction essentially creates a brand new "root" of the B-tree. To get a consistent snapshot, a transaction just attaches itself to a specific root; it doesn't need to filter out objects based on transaction IDs because subsequent writes only create *new* roots, leaving the old tree intact.
    * *The Downside:* Because pages are constantly copied and never overwritten, this approach requires a robust background process for compaction and garbage collection to prevent the disk from filling up.
# Preventing Lost Updates
The **Lost Update Problem** occurs in a *read-modify-write cycle*. If two transactions read a value, modify it, and write it back concurrently, the later write clobbers (overwrites) the earlier write, destroying data.
* *Examples:* Incrementing a counter, adding an element to a JSON list, or two users editing a Wiki page simultaneously.

Databases offer a few ways to solve this:
1.  **Atomic Write Operations:** Removes the need to implement read-modify-write in your application code (e.g., `UPDATE counters SET value = value + 1`). 
    * *How it works:* The database takes an exclusive lock on the object when it is read, forcing the operations to happen on a single thread.
2.  **Explicit Locking:** If the DB's atomic operations aren't enough (e.g., you need to run complex game logic in your application before updating), the application can explicitly lock the objects (e.g., using `SELECT * FROM ... FOR UPDATE`).
3.  **Automatically Detecting Lost Updates:** Instead of forcing locks, allow transactions to execute in parallel. If the transaction manager detects a lost update occurred, it aborts the offending transaction and forces the application to retry. (Postgres does this; MySQL does *not*).
4.  **Compare-and-Set:** Allows an update to happen *only* if the value has not changed since you last read it (e.g., `UPDATE wiki SET content = 'new' WHERE content = 'old'`). If another user changed the content, the WHERE clause fails, and the update has no effect.
    * ***The Snapshot Trap:*** This is only safe if the database implementation guarantees the `WHERE` clause reads the *currently committed* value from disk. If the database executes the `WHERE` clause against an *old snapshot* (which happens in some MVCC implementations), the condition will evaluate to true even if another transaction just changed the value, and the lost update will still happen. Always check if your database's compare-and-set operation is actually safe under its default isolation level!

## Conflict Resolution and Replication
Preventing lost updates takes on another dimension in replicated databases.
* **The Problem with Locks:** Locks and Compare-and-Set operations assume there is a **single up-to-date copy of the data** (i.e., a Single-Leader architecture). In Multi-Leader or Leaderless databases (like Cassandra or DynamoDB), taking a lock on Node A does nothing to stop a user from concurrently writing to Node B.
* **The Sibling Solution:** Because there is no single source of truth to lock, these databases generally allow concurrent writes to proceed, creating conflicting versions of a value (known as **siblings**). It is then up to the application code (or special data structures) to resolve and merge these versions after the fact.
* **The Exception (Commutative Atomic Operations):** Atomic operations *can* work in a replicated context, but **only if they are commutative** (meaning you can apply them in different orders on different replicas and still get the exact same result).
    * *Example:* Incrementing a counter or adding an element to a set are commutative operations. Riak leverages this for its datatypes to prevent lost updates across replicas automatically.

# Write Skew and Phantoms
Write skew is a subtle race condition that occurs when two transactions read the *same* objects, but then update *different* objects based on that premise. It is a generalization of the lost update problem.
* **The Classic Example (Doctors on Call):** A hospital requires at least 1 doctor on call. Alice and Bob are currently on call. Both feel sick and concurrently click "take me off call." 
    * Alice's transaction checks: `SELECT count(*) WHERE on_call = true`. Result: 2.
    * Bob's transaction checks: `SELECT count(*) WHERE on_call = true`. Result: 2.
    * Both transactions decide it is safe to proceed. Alice updates *her own* record to false. Bob updates *his own* record to false. 
    * Both commit. Result: 0 doctors on call. The business requirement is violated.
* **Other Examples:** Double-booking a meeting room, two players moving different pieces to the exact same board position, claiming the same username, or double-spending an account balance.

### Preventing Write Skew
Write skew is notoriously hard to prevent because multiple objects are involved, meaning single-object atomic operations do not help. Furthermore, standard Snapshot Isolation/Repeatable Read does *not* detect it.
1.  **True Serializable Isolation:** The most robust solution.
2.  **Database Constraints:** If applicable, rely on the database's built-in uniqueness or foreign key constraints (e.g., a `UNIQUE` index safely prevents the "claiming a username" write skew).
3.  **Explicit Locking:** If you can't use serializability, lock the rows the transaction depends on using `SELECT ... FOR UPDATE`.

## The Phantom Problem
The examples above all share a dangerous pattern:
1.  A `SELECT` query checks a precondition (e.g., "Are there overlapping bookings?").
2.  The application code processes the result and decides to go ahead.
3.  The application makes an `INSERT/UPDATE/DELETE` and commits.

**The catch:** The write in step 3 changes the precondition of the decision in step 2. If you were to run the `SELECT` query again, you would get a different result. **This effect—where a write in one transaction changes the result of a search query in another transaction—is called a phantom.**

### Materializing Conflicts (A Design Decision)
If your write skew is caused by an `UPDATE` (like the doctors example), you can lock the existing rows. But what if the phantom is an `INSERT` (like booking an empty meeting room)? You cannot lock a row that doesn't exist yet!

To solve this, you have to make a specific **design decision**: if there is no object to attach a lock to, you can *artificially introduce one*. 
* **The Implementation:** For the meeting room, you could create a table of all possible 15-minute time slots for the next 6 months. Now, a transaction can explicitly `SELECT FOR UPDATE` that specific time slot row before inserting the booking. 
* **The Verdict:** This approach is called **materializing conflicts** (because it takes a phantom and turns it into a lock conflict on a concrete set of rows). It is generally considered a hacky last resort because it leaks your concurrency control mechanism directly into your application's data model. A serializable isolation level is much preferable in most cases.
# Serializability
Because weak isolation levels are a minefield of subtle bugs (like write skew), researchers have long advocated for **Serializable Isolation**. It is the strongest isolation level. 
* **The Guarantee:** Even though transactions may execute in parallel, the database guarantees that the end result is the exact same as if they had executed *one at a time, serially*.
Most databases implement serializability using one of three techniques. The first is:
## 1. Actual Serial Execution
The simplest way to avoid concurrency problems is to completely remove concurrency: execute only one transaction at a time, in serial order, on a single thread. 

For 30 years, database designers thought this was impossible due to performance limitations, but two developments changed their minds:
1.  **RAM became cheap:** The entire active dataset can now fit in memory, meaning transactions execute much faster without waiting for disk I/O.
2.  **OLTP vs. OLAP distinction:** Database designers realized that **OLTP** (Online Transaction Processing) transactions are usually very short and only make a small number of reads/writes. Because they are so short, a single thread can process tens of thousands of them per second. Long-running **OLAP** (Online Analytical Processing) queries are intentionally run *outside* of this serial loop on a read-only snapshot so they don't block the fast OLTP writes.
### Design Decision: Stored Procedures
If a database processes one transaction at a time on a single thread, it cannot wait for the application to send a query, think about the result, and send a second query. The network latency back and forth would stall the single thread and bring the database to a halt.
* *The Solution:* Systems like Redis and VoltDB force the application to submit the *entire transaction logic* ahead of time as a **Stored Procedure** (written in Lua, Java, etc.). 
* *The Result:* Because the logic executes locally in the database, the data is entirely in RAM, and there is zero network I/O or locking overhead, this single-threaded loop achieves mind-boggling throughput.
#### Pros and Cons of Stored Procedures
Historically, stored procedures have had a terrible reputation among software engineers for three main reasons:
1.  **Archaic, Vendor-Specific Languages:** Oracle uses PL/SQL, SQL Server uses T-SQL, PostgreSQL uses PL/pgSQL. These languages are generally considered ugly and lack the rich ecosystem of libraries found in modern general-purpose languages.
2.  **Hard to Manage:** Code running in a database is much harder to debug, version control, test, and monitor compared to code running on a standard application server.
3.  **Performance Blast Radius:** A database instance is shared across the entire system. A poorly written, CPU-heavy stored procedure can tank the entire database, whereas a bad script on an app server just kills one isolated pod.
**The Modern Comeback:** Modern single-threaded databases overcame these issues by abandoning archaic SQL dialects and adopting existing, general-purpose languages (e.g., Redis uses Lua; VoltDB uses Java/Groovy). 
* *Replication Nuance (VoltDB):* Instead of copying massive amounts of written data from node to node, VoltDB performs replication by executing the exact same stored procedure on every replica. Because of this, VoltDB requires that all stored procedures be strictly **deterministic** (e.g., if the code requires the current date/time, it must use a special deterministic API so all nodes get the exact same timestamp).
### The Limits: Partitioning
Single-threaded execution is hard-capped by the speed of a single CPU core. To scale, databases partition the data (giving each CPU core its own partition and its own transaction processing thread). 
* **The Catch:** If a transaction needs to read/write across *multiple partitions*, the database must coordinate the transaction in lock-step across all involved partitions. This makes cross-partition transactions **vastly slower** than single-partition ones.

## 2. Two-Phase Locking (2PL)
For around 30 years, Two-Phase Locking was the only widely used algorithm for ensuring serializability. 
Unlike Snapshot Isolation (where readers never block writers and vice-versa), 2PL enforces a much stricter rule: **Writers block readers, and readers block writers**. Several transactions can concurrently read the same object, but the moment anyone wants to write to it, they require exclusive access.
### Implementation Details
2PL is implemented by having a lock on each object in the database, used in either *shared mode* or *exclusive mode*.
* If a transaction wants to read, it acquires a shared lock.
* If a transaction wants to write, it must acquire an exclusive lock.
* **The "Two Phases":** The first phase occurs while the transaction is executing and locks are being acquired. The second phase occurs at the end of the transaction (commit or abort) when all locks are released simultaneously.

### The Performance Cost
The major downside of 2PL is terrible performance. Transaction throughput and response times are significantly worse than under weak isolation. 
* **Instability:** Databases running 2PL have highly unstable latencies. A single slow transaction that acquires many locks can cause a queue to form, grinding the entire system to a halt.
* **Deadlocks:** Because transactions are constantly waiting on each other, deadlocks occur very frequently. The database automatically detects this and aborts one transaction to break the loop, meaning the application must retry it from scratch (wasted effort).

### Predicate Locks and Index-Range Locks
To prevent phantoms (where one transaction changes the results of another's search query), 2PL databases face a unique problem: you cannot put a physical shared or exclusive lock on a row that hasn't been inserted yet. 

To solve this, the database must lock objects that *do not even exist yet*. 
* **Predicate Locks:** Instead of locking a physical row, the database locks a *search condition* (a predicate). A predicate lock belongs to all objects that match that condition (e.g., "lock any booking where `room_id = 123` AND `time = 12:00`"). If another transaction tries to insert, update, or delete any object that matches this currently locked condition, it must wait.
* **Index-Range Locking (Next-Key Locking):** Because true predicate locks are extremely slow to compute (the database would have to check every active predicate against every new insert), most databases implement a simplified approximation called index-range locking.
    * The database simplifies the search condition and attaches a shared lock directly to a broader index entry (e.g., instead of locking just the 12:00 time slot, it locks the entire index entry for `room_id = 123`).
    * If there is no suitable index where a range lock can be attached, the database falls back to placing a shared lock on the *entire table*. This is completely safe, but it brings concurrent writes to a standstill.
> ### **Deep Dive: The Internal Mechanics of the Lock Manager**
> When a transaction locks multiple objects (rows, pages, or tables), the database does not write a "locked" flag to the physical disk. Disk I/O is too slow. Instead, all locks are purely logical data structures managed entirely in RAM by a dedicated background component called the **Lock Manager**.
> 
> Regardless of what isolation level you are using, the Lock Manager fundamentally operates using three concepts:
> 
>  **1. The Lock Table (A Giant Hash Map)**
> The core of the Lock Manager is a massive, highly optimized in-memory Hash Table. 
> * **The Key:** A unique identifier for the object being locked (e.g., `TableID : PageID : RowID`).
> * **The Value:** A linked list (or queue) of "Lock Request" objects. 
> 
> When your transaction requests a lock on 5 different rows across 3 different tables, the Lock Manager simply hashes those 5 physical locations and creates 5 distinct entries in the Lock Table. Each entry records your `Transaction_ID`, the `Lock_Mode` (Shared/Exclusive), and the `Status` (Granted/Waiting). 
> * *Wait-For Graphs:* If your transaction needs a row that is already locked, you are added to the end of that row's linked list with a status of `Waiting`. A background thread constantly scans these linked lists looking for cycles to detect deadlocks.
> 
>  **2. Intent Locks (The Hierarchy Problem)**
> If Transaction A holds an Exclusive lock on Row 5 in Table X, what happens if Transaction B suddenly requests an Exclusive lock on the *entire* Table X? 
> 
> The Lock Manager cannot afford to scan a billion rows in Table X just to see if a single row is currently locked. To solve this, databases use **Intent Locks**.
> * Whenever a transaction locks a row, the Lock Manager automatically places an **Intention Exclusive (IX)** or **Intention Shared (IS)** lock on the parent structures (the memory page, and the table itself).
> * If Transaction B wants to lock the whole table, it instantly sees the IX lock on the table header and knows it must wait. It doesn't need to scan the rows.
> 
>  **3. Lock Escalation (The Memory Problem)**
> Because the Lock Table lives in RAM, it has finite space. Every lock takes up a few bytes of memory. If you run a massive `UPDATE` statement that touches 10 million rows, you would generate 10 million entries in the Lock Table, exhausting the database's RAM and crashing the server.
> 
> To prevent this, the Lock Manager uses **Lock Escalation**. 
> * The database tracks how many row-level locks a single transaction holds. 
> * Once a threshold is crossed (e.g., 5,000 locks on a single table in SQL Server), the Lock Manager dynamically swaps them out. It acquires a single Exclusive lock on the *entire table* and deletes the 5,000 individual row-level locks from RAM to save memory. 
> * *The Trade-off:* This saves the database from crashing, but it destroys concurrency. Suddenly, every other transaction trying to write to that table is blocked until your massive update finishes.
## 3. Serializable Snapshot Isolation (SSI)
SSI is a modern algorithm that provides full serializability but has only a small performance penalty compared to standard snapshot isolation. 
* **Pessimistic vs. Optimistic:** 2PL and Serial Execution are *pessimistic* (they wait until a situation is completely safe before proceeding). SSI is an **optimistic** concurrency control technique. 
* **How it works:** Transactions continue to execute freely in the hope that everything will turn out fine. When a transaction wants to commit, the database checks if isolation was violated. If it was, the transaction is aborted and must be retried.
	* **Why wait until committing?:** The database waits until commit time to abort because 
		* the other transaction might be read-only (meaning no risk of write skew)
		* the other concurrent transaction might fail and abort anyway. 
		* the other concurrent transaction might still be uncommitted

### Detecting Outdated Premises
Under SSI, the database must detect if a transaction is taking an action based on a premise that is no longer true. It tracks this by looking for two specific cases:

**Case 1: Detecting reads of a stale MVCC object version**
When a transaction reads from a snapshot, it ignores writes from other uncommitted transactions. When the reading transaction wants to commit, the database checks if any of those previously ignored writes have now been committed. If they have, the transaction must be aborted.

**Case 2: Detecting writes that affect prior reads**
When a transaction writes to the database, it looks at the indexes to see what other transactions have recently read the affected data. It does not block them; instead, the lock acts as a tripwire, simply notifying the reading transaction that its data is no longer up to date.

### The Performance Advantage of SSI
The biggest advantage of SSI over 2PL is that **transactions do not block waiting for locks held by others**. Writers do not block readers, keeping query latency low and predictable.

Furthermore, unlike Actual Serial Execution (which must physically force everything through a single CPU core to avoid concurrency), SSI allows for true multi-threaded parallel execution. The database simply tracks a ledger of who read and wrote what. Because this conflict-detection ledger is just tracking data access, systems like FoundationDB can partition it across multiple machines, allowing transaction throughput to scale horizontally to a massive degree.

**The Trade-off (Contention):** Because SSI relies on aborting and retrying transactions rather than blocking them, it performs poorly under highly contended workloads (where everyone is trying to update the exact same objects simultaneously). Under high contention, the system wastes massive amounts of CPU cycles processing transactions that will inevitably be aborted.
# Margin Notes:

## The Race Conditions (The Anomalies)
* **Dirty Reads:** One client reads another client's writes before they have been committed. (Prevented by Read Committed and stronger levels).
* **Dirty Writes:** One client overwrites data that another client has written, but not yet committed. (Prevented by almost all transaction implementations).
* **Read Skew (Nonrepeatable Reads):** A client sees different parts of the database at different points in time. (Prevented by Snapshot Isolation using MVCC).
* **Lost Updates:** Two clients concurrently perform a read-modify-write cycle. One overwrites the other's write without incorporating its changes, destroying data. (Prevented automatically by *some* Snapshot Isolation implementations, or manually via `SELECT FOR UPDATE` / atomic operations).
* **Write Skew:** A transaction reads something, makes a decision based on that value, and writes the decision. By the time the write is made, the premise of the decision is no longer true. (Only prevented by true Serializable isolation).
* **Phantom Reads:** A transaction reads objects that match a search condition. Another client makes a write that affects the results of that search. (Phantoms causing write skew require special treatment, such as index-range locks).

## Concurrency Confusion

| Feature | OS / CPU Concurrency | Database Concurrency |
| :--- | :--- | :--- |
| **Core Definition** | Overlapping **execution time** (Interleaving). | Overlapping **data access** (Transactions). |
| **The Primary Goal** | Maximize resource utilization (keep the CPU busy). | Protect data integrity (maintain the ACID illusion). |
| **The Mechanism** | Thread scheduling, context switching, time-slicing. | Lock Managers (2PL), MVCC (Snapshots), SSI tripwires. |
| **The Enemy** | Idle time, blocking I/O, unresponsive UI. | Race conditions, dirty reads, lost updates, write skew. |
| **The "Ideal" State** | Everything runs at exactly the same time. | Everything runs as if it were the *only* thing running (Serializability). |
