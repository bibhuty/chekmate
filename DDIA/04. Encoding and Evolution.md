# The Core Problem: Evolvability
- **The Reality of Change:** Applications change over time; features are added, and data models adapt. However, in a large application, code changes often cannot happen instantaneously.
- **The Rollout Problem:** With server-side applications, you perform a rolling upgrade (staged rollout) to avoid downtime. With client-side applications, you are at the mercy of the user to install the update.
- **The Compatibility Mandate:** Because old and new versions of code coexist in the system, you must maintain compatibility in both directions:
  - **Backward Compatibility:** Newer code can read data written by older code. (Usually easy, as the new code explicitly knows the old format).
  - **Forward Compatibility:** Older code can read data written by newer code. (Tricky, because the old code must gracefully ignore new additions).

# Formats for Encoding Data (The Serialization Tax)
Programs operate with data in two entirely different representations:
1. **In-Memory:** Data is kept in objects, structs, or hash tables. These are optimized for efficient CPU access, typically using memory pointers.
2. **On-the-Wire (or On-Disk):** Pointers make no sense to another process or server, so data must be translated into a self-contained sequence of bytes (like a JSON document).
- **The Translation:** Translating from in-memory to byte sequences is called **Encoding** (or serialization/marshalling). The reverse is **Decoding** (parsing/deserialization).

## 1. Language-Specific Formats (The Anti-Pattern)
Languages have built-in encoding (e.g., Java's `Serializable`, Python's `pickle`).
- **The Flaws:** They tie you to one specific programming language. Decoding requires instantiating arbitrary classes, which is a massive security vulnerability (allowing remote code execution). Versioning and performance are generally terrible.
- **The Operational Rule:** Because language-specific formats are strictly for transient(short-lived, temporary, or impermanent) communication, they must **never** be used for persistent storage (like saving to a database) or exposed over public network APIs.

## 2. JSON, XML, and CSV (The Human-Readable Illusion)
While standardized and human-readable, textual formats carry subtle but devastating bugs at scale.
### Number Ambiguity in XML & CSV
These formats cannot inherently distinguish between a mathematical number and a string that just happens to consist of digits. 
- *Example:* In XML (`<value>42</value>`) or a CSV cell (`42`), the parser has no idea if you intend for this to be the integer 42 or the text string `"42"`.
### Precision Ambiguity in JSON
JSON successfully distinguishes strings (`"42"`) from numbers (`42`), but it does *not* specify precision (i.e., it doesn't differentiate between integers and floating-point numbers).
- *Real-World Example (The E-commerce Crash):* An API parses incoming JSON into a generic data map (like Java's `Map<String, Object>`). If a user buys an item for $19.99, the JSON is `{"price": 19.99}`. The parser sees the decimal, guesses it is a `Double` (float), and saves it. Your backend reads it perfectly. However, if the next user buys a hat for exactly $20, the JSON is sent as `{"price": 20}`. The parser sees no decimal, guesses it is an `Integer`, and saves it as an integer. When your backend code attempts to extract the price as a `Double`, the application throws a `ClassCastException` (Type Mismatch) and the entire checkout process crashes.
### The Large Integer Crash
Integers greater than $2^{53}$ cannot be exactly represented in IEEE 754 floating-point. (e.g., Twitter uses 64-bit integers for Tweet IDs. JavaScript parses them as floating-point numbers, rounding them off and corrupting the ID. Twitter's API had to start returning IDs twice: once as a number, once as a string).
- *The Hardware Limit (IEEE 754):* IEEE 754 is the global hardware standard for storing decimals in memory. It works exactly like scientific notation, storing the fraction and the exponent separately. A 64-bit float rigidly divides its memory into 1 bit for the Sign, 11 bits for the Exponent, and 52 bits for the Fraction.
- *The Crash Mechanism:* You only have 52 bits (plus 1 hidden implicit bit) to store exact digits. Therefore, $2^{53} - 1$ is the absolute maximum integer where every single digit is perfectly accurate. If you try to store a number larger than that, the computer runs out of fraction bits. To make the massive number fit in memory, it forces the exponent to take over, which structurally rounds off the final digits. It literally loses the ability to count by 1s!
### Binary Data Bloat
Text formats support Unicode and do not support raw binary strings. You must encode binary data as Base64 text, which increases the data size by 33%.
- *What is a Binary String?* It is raw, unformatted computer data, such as a compressed `JPEG` profile picture, a compiled `.exe` file, or a cryptographic hash (like an AES encryption key). If you try to send a raw JPEG directly inside a JSON payload, the JSON parser will crash because the raw bytes don't represent valid text characters. 
### Optional Schemas (XML & JSON)
Both formats *do* support optional schema languages to enforce rules, but they are incredibly complex to learn and implement. While XML schemas are widely used, JSON schemas are frequently ignored by developers. 
- *The Trap:* If you don't use a schema, the receiving application must hardcode the logic to interpret the data types.
- *Example:* A JSON Schema can explicitly enforce `{"price": {"type": "number"}}`. Without this schema attached to the payload, the receiving backend has to write manual, brittle `if/else` validation code to check if the incoming price was sent as a string (`"19.99"`) or a float (`19.99`) before letting it touch the database.

CSV has zero schema support. The application itself must blindly trust the row and column order.
- *Manual Evolution:* If you add a new column to a CSV export, you must manually update the code of every single application that reads it, or they will parse the columns out of order.

## 3. Binary JSON Variants (MessagePack, BSON)
Formats like MessagePack attempt to convert JSON to binary to save space.
- **The Failure:** Because they don't prescribe a schema, they must keep the JSON/XML data model unchanged. They still have to physically write the field names (e.g., `"userName"`) into the encoded data.
### Why is MessagePack smaller than JSON?
JSON wastes bytes on structural text characters (`{`, `"`, `:`) and stores numbers as individual text characters. MessagePack replaces these with single-byte binary tags. 
### What exactly is a Tag?
It is not a hex string, and it is not a placeholder. It is a literal, raw **8-bit binary byte** dictated by the official MessagePack specification. It acts as a structural header that tells the CPU exactly what data type is coming next, and for short fields, exactly how long it is. *(Humans write these tags in Hexadecimal, like `0x81`, just to make them readable, but on the network wire, it is purely electrical 1s and 0s).*
### The Simplest Example: `{"id": 42}`
- **JSON (9 bytes):** Needs 1 byte for every single text character: ` { ` ` " ` ` i ` ` d ` ` " ` ` : ` ` 4 ` ` 2 ` ` } `
- **MessagePack (5 bytes):** The exact raw bytes sent over the network are `81 A2 69 64 2A`:
  1. **`81` (The Map Tag):** Binary `10000001`. The `1000` means "short map", and the `0001` means "contains 1 item".
  2. **`A2` (The String Tag):** Binary `10100010`. The `101` means "short string", and the `00010` means "length of 2 characters".
  3. **`69`:** Standard ASCII binary for the letter 'i'.
  4. **`64`:** Standard ASCII binary for the letter 'd'.
  5. **`2A` (The Integer Tag):** Binary `00101010`. The `0` means "short positive integer", and `0101010` is exactly the number 42.
### The Catch
MessagePack successfully saved 4 bytes by optimizing the syntax and squishing the number, but **it still had to physically store the letters "i" and "d"**(the field name). At massive scale, this is a half-measure. True schema-based encodings (like Protobuf) delete the "id" string entirely.

# Binary Encoding via Schemas (Thrift & Protocol Buffers)
Apache Thrift (Facebook) and Protocol Buffers (Google) solve the space issue by demanding a strict schema. 
- **The Superpower (Field Tags):** There are no field names (like `"userName"`) in the encoded data. Instead, the schema maps the name to a **Field Tag** (the numbers 1, 2, 3). The binary data only contains these tiny integer tags.
- **The Required/Optional Illusion:** Marking a field as `required` or `optional` in your schema makes absolutely **zero difference** to how the data is physically encoded into binary bytes. 
## Code Generation (The Engineering Superpower)
While field tags optimize the network, code generation optimizes the engineering team. Both Thrift and Protobuf come with a command-line tool for this exact purpose.
- **How it Works:** You define your schema once in a `.thrift` or `.proto` file. The command-line tool then reads that file and automatically generates the classes/structs for your specific programming language (e.g., Java, C++, Go).
- **Compile-Time Safety:** In statically typed languages, the generated code provides strict type checking. If a developer tries to assign a string to an integer field, the code instantly fails to compile. You catch the bug in your IDE before the code is ever deployed.
- **No Manual Parsing:** The generated classes completely abstract away the complex bitwise math of encoding and decoding the binary tags. The application code simply interacts with native, familiar objects (e.g., `user.setUserName("Alice")`), and the generated library does all the heavy lifting under the hood.
## How Does Thrift Pack Bytes?
Apache Thrift offers two primary ways to physically encode data into binary. This choice represents a classic systems architecture trade-off: **CPU Speed vs. Network Bandwidth**.

| Feature          | `BinaryProtocol`                                                                                     | `CompactProtocol`                                                                                       |
|:-----------------|:-----------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------|
| **Philosophy**   | Optimize for the CPU (Fast to read)                                                                  | Optimize for the Network (Small to send)                                                                |
| **Integer Size** | **Fixed-Width.** An `int32` always takes exactly 4 bytes of memory, even if the number is just `42`. | **Variable-Length.** Squishes numbers down. Small numbers like `42` take only 1 byte.                   |
| **Field Tags**   | Tags take a fixed 2 bytes. Types take 1 byte.                                                        | Packs the Field Tag and the Data Type into a single shared byte.                                        |
| **CPU Overhead** | **Low.** The CPU can read the bytes instantly because the spacing is completely predictable.         | **High.** The CPU has to perform bitwise math on every single byte to figure out where the number ends. |

#### The Space Management Example (Thrift)
Let's use our simple example of `{"id": 42}` and assume our schema is `int32 id = 1;`.

* **JSON (9 bytes):** `{`, `"`, `i`, `d`, `"`, `:`, `4`, `2`, `}`
* **Thrift `BinaryProtocol` (7 bytes):** Predictable and rigid.
  1. **Type:** `08` (1 byte explicitly saying "This is a 32-bit integer")
  2. **Tag:** `00 01` (2 bytes explicitly saying "This is Tag 1")
  3. **Value:** `00 00 00 2A` (4 bytes explicitly reserving the full 32-bit space for the number 42)
* **Thrift `CompactProtocol` (2 bytes):** Aggressively compressed.
  1. **Type & Tag:** `15` (1 byte that mathematically combines the Type `i32` and the Tag `1`)
  2. **Value:** `2A` (1 byte. Because 42 is so small, it drops the leading zeros and fits into a single byte).

## How Does Protocol Buffers (Protobuf) Pack Bytes?
Protocol Buffers (Google's equivalent to Facebook's Thrift) follows the exact same architectural philosophy, but it only has one primary binary encoding format. 
Protobuf's encoding works almost identically to Thrift's `CompactProtocol`. It heavily relies on bit-packing and **Variable-Length Integers (Varints)** to ensure that tiny numbers don't waste massive amounts of network bandwidth.
#### The Space Management Example (Protobuf)
Using the exact same payload `{"id": 42}` and schema `int32 id = 1;`:
* **Protobuf (2 bytes):**
  1. **Type & Tag:** `08` (1 byte. Protobuf uses a bitwise formula `(field_number << 3) | wire_type`. Tag 1 and Type 0 result in the binary `00001000`, which is Hex `08`).
  2. **Value:** `2A` (1 byte. Protobuf drops the leading zeros and stores the integer 42 dynamically).

> 💡 **Architect's Sidenote: How do ASCII, Unicode, and UTF-8 glue together?**
> To understand variable-length integers (like Protobuf/Thrift), it helps to understand variable-length text (UTF-8). Here is how the three text standards snap together into a single system:
> 
> **1. ASCII (The Ancient Foundation):** Created in the 1960s, it uses exactly 7 binary bits to represent 128 characters (A-Z, 0-9, and basic punctuation). It physically cannot hold enough information to support other languages.
> 
> **2. Unicode (The Global Dictionary):** This is a theoretical dictionary, not a file format. It took ASCII, kept it exactly as it was, and then added millions of new numbers to support Arabic, Kanji, and Emojis. For example, 'A' is assigned the number 65. '😊' is assigned the number 128,510.
> 
> **3. UTF-8 (The Physical Delivery Mechanism):** UTF-8 is the physical byte-packing strategy (just like Thrift's `CompactProtocol`). It is a **variable-length encoding**.
> * If you type 'A' (Unicode 65), UTF-8 realizes it is a tiny ASCII number and squishes it into **1 single byte**.
> * If you type '😊' (Unicode 128,510), UTF-8 realizes it is a massive number, dynamically expands, and uses **4 bytes** to store it. 
> * **The Glue:** Because UTF-8 uses exactly 1 byte for standard English letters, any ancient system built for ASCII can read a modern UTF-8 file perfectly without crashing. It is the ultimate backward-compatible standard.

## Schema Evolution (The Rules of Thrift/Protobuf)
Records are simply concatenated fields identified by their integer tags. 
### 1. The Core Rules
- **The Golden Rule:** Never change or recycle a tag number. You can safely rename fields.
- **Forward Compatibility (Old reads New):** Old code uses the datatype's byte-length annotation to silently skip unrecognized new tags.
- **Backward Compatibility (New reads Old):** New fields **must** be optional or have a default. If new code strictly requires a new field, reading old data will instantly crash the app.
- **Removing Fields:** You can only delete optional fields, and the tag number is permanently retired.
- **The Required/Optional Illusion:** Marking a field `required` changes absolutely nothing about the physical binary bytes; it is strictly a runtime check. Because it causes so many backward-compatibility crashes, Protobuf v3 deleted the `required` keyword entirely.
### 2. Datatype Evolution
Changing a field's actual data type carries severe risks for precision and compatibility.
- **Changing Integer Sizes (The Truncation Risk):** If you upgrade an integer from 32-bit to 64-bit:
  - *Backward Compatible (Success):* New code safely reads old 32-bit data by padding the empty space with zeros.
  - *Forward Compatible (The Catch):* Old code only has 32 bits of memory space. If it reads a new, massive 64-bit number, it silently chops off (truncates) the extra bits, completely corrupting the value.
- **Evolving Single Values to Lists:**
  - *Protobuf (`repeated` marker):* A list is just the exact same field tag sent multiple times in a row. You **can** safely upgrade a single field to a list. New code reads old data as a list of 1. Old code reading a new list simply overwrites the variable each time it sees the tag, safely keeping only the *last* item.
  - *Thrift (Dedicated List Type):* Uses a strict, explicit list data type. You **cannot** seamlessly upgrade a single value to a list; the parser will throw a type mismatch error. However, because it is a real data type, Thrift natively supports **nested lists**, which Protobuf's `repeated` marker cannot do.
# Apache Avro (The Tagless Paradigm)
Avro (born from Hadoop) takes binary encoding a step further: **There are no tag numbers in the schema**.
## How Does Avro Pack Bytes? (The Missing Types)
When you look at an Avro schema, you clearly see data types defined (e.g., `{"name": "id", "type": "int"}`). However, if you inspect the raw binary data sent over the network, those types completely vanish. 
- **The Schema is an Instruction Manual, not a Payload:** In Protobuf, the binary stream explicitly announces "Here comes an integer!" using a wire type byte. Avro doesn't do this. The receiving parser simply looks at its local schema, sees that the first field is defined as an `int`, and blindly grabs the next bytes off the network wire, mathematically assuming they must represent an integer. 
#### The Space Management Example (Avro)
Let's look at how Avro physically encodes our standard payload `{"id": 42}` assuming the schema dictates the first field is an `int`:
* **JSON (9 bytes):** `{`, `"`, `i`, `d`, `"`, `:`, `4`, `2`, `}`
* **Protobuf (2 bytes):** `08` (Type/Tag) + `2A` (Value)
* **Avro (1 byte):** 1. **Value:** `54` (Avro uses a specific variable-length math called ZigZag encoding. To save space, it transforms 42 into 84, which is Hex `54`).
  2. **That's it.** There is no Type byte. There is no Tag byte. The string "id" is gone. 
**The Risk of Blind Parsing:** Because the bytes themselves offer absolutely zero clues about what data type they belong to, the reader **must** have the exact same schema. If the reader's schema says the first field is a `string`, it will blindly decode that Hex `54` into a random text character, instantly corrupting the data without throwing an error.

## Avro Schema Evolution (Writer vs. Reader)
- **Writer's Schema:** The schema the application knows about when it encodes the data.
- **Reader's Schema:** The schema the application is expecting to use when it decodes the data.
- **The Avro Magic:** The writer’s schema and reader’s schema don’t have to be identical—they just need to be **compatible**. The Avro library looks at both schemas side-by-side and translates them. If the writer added a field the reader doesn't know, it ignores it. If the reader expects a field the writer didn't provide, it fills it with a default value.
- **The Evolution Rule:** To maintain compatibility in Avro, you may **only add or remove a field that has a default value**.
### The Trickiness of Changing Names and Datatypes
Avro's strict reliance on matching schemas creates unique rules for modifying existing fields.
- **Changing Field Names (The Alias Trap):** - *Backward Compatible (Success):* You deploy a New Reader. You tell its schema, "The field is now called `user_id`, but its **alias** used to be `userName`." When it reads old data, it uses the alias to map the bytes perfectly.
  - *Forward Compatible (Fails):* You deploy a New Writer that outputs `user_id`. An Old Reader pulls the data. It strictly expects `userName`, has no idea what `user_id` or the new alias is, and fails to read the field.
- **Changing Datatypes:** You can change a datatype only if Avro supports the implicit mathematical conversion (e.g., safely upgrading an `int` to a `long`). Changing to an incompatible type will instantly break the reader, as it will try to blindly apply the wrong decoding math to the raw binary bytes.

## But how does the Reader get the Writer's Schema?
If the binary data doesn't contain the schema, how does the system know what to do? It depends on the architecture:
1. **Large Files (Hadoop):** The writer's schema is just pasted once at the very top of the massive file.
2. **Databases (Individual Records):** Include a tiny version number at the beginning of every record. The database maintains a table of schema versions to look up the correct writer's schema.
3. **Network RPC:** The client and server negotiate the schema version during the connection setup handshake.
## Avro's Hidden Advantage: Dynamic Schemas
Avro is far friendlier to dynamically generated schemas.
If you want to dump a relational database table to a file, Avro can generate a schema on the fly based on the column names. If you used Protobuf/Thrift, an engineer would have to manually assign integer tags (1, 2, 3) to every single database column, and manage those tags if the database schema ever changed.
## The Merits of Schemas (Why we do this)
Although JSON is easy to read, binary encodings based on schemas (Thrift, Protobuf, Avro) provide critical architectural guarantees:
1. **Bandwidth:** They are incredibly compact because they omit field names.
2. **Source of Truth:** The schema serves as highly valuable, executable documentation.
3. **Safety:** Keeping a database of schemas allows you to check for forward/backward compatibility breakages programmatically *before* code is ever deployed to production.
4. **Compile-Time Checks:** For statically typed languages, the generated code provides compile-time type checking, catching bugs in the IDE rather than the server.
# Modes of Dataflow (How Data Travels)
Whenever you want to send data to another process with which you don't share memory, you must encode it as a sequence of bytes. Compatibility is fundamentally a relationship between the process that *encodes* the data and the process that *decodes* it. This happens in three primary ways:

## 1. Dataflow Through Databases (Sending a Message to Your Future Self)
In a database, the process writing the data encodes it, and the process reading the data decodes it. 
- **The Golden Rule: Data Outlives Code:** Application code is entirely replaced during a deployment rollout taking a few minutes. Database contents are not. A five-year-old row will still be sitting on disk in its original encoding unless explicitly rewritten.
- **The "Lost Field" Update Trap:** Imagine New Code adds a field and writes it to the database. Old Code (which doesn't know about the field) reads that record, updates a *different* value, and saves the whole record back. If the Old Code's framework isn't careful, it will strip out the unknown new field entirely during the save process.
- **Archival Storage & Data Dumps:** When taking a snapshot of a database for a data warehouse, the database often contains a messy mixture of historical schema versions. 
  - *The Strategy:* The entire dump is uniformly encoded using the *latest* schema. 
  - *The Format:* Because a data dump is written in one single pass and is completely immutable thereafter, **Avro** is the perfect format for this job.

## 2. Dataflow Through Services (REST vs. RPC)
When clients and servers communicate over a network, the API exposed by the server is known as a **service**. When a server acts as a client to *another* server, it is called a **Service-Oriented Architecture (SOA)**, or more recently, **Microservices**. 

If the underlying protocol is HTTP, it is called a *web service*. 

### The RPC Illusion (Location Transparency)
Remote Procedure Calls (RPC) were built on the idea of **Location Transparency**—the attempt to make a network request look and act exactly like calling a local function in your programming language. This abstraction is fundamentally flawed because local functions and network calls are entirely different beasts:

| Feature | Local Function Call | Network Request (RPC) |
| :--- | :--- | :--- |
| **Predictability** | Succeeds or fails based strictly on your parameters. | Completely unpredictable. Packets get lost, remote machines crash or overload. |
| **Outcomes** | Returns a result, throws an exception, or infinite loops. | Can return *nothing* due to a **Timeout**. You have no idea if the request failed, or if it succeeded and only the *response* was lost. |
| **Retries & Safety** | Not applicable. | If you retry a timed-out request that actually succeeded, you execute it twice. You must manually build **Idempotence** (deduplication) into the protocol. |
| **Performance** | Consistently fast execution. | Wildly variable latency depending on network congestion. |
| **Memory** | Efficiently passes pointers to local memory objects. | Must physically encode all parameters into byte sequences (terrible for large objects). |

### The REST Philosophy
REST is not a protocol; it is a design philosophy built on HTTP. 
- **Embracing the Network:** Unlike traditional RPC, REST does not try to hide the fact that it is a network protocol. It utilizes URLs, cache control, and authentication natively.
- **The Ecosystem Advantage:** While a custom binary RPC is faster, RESTful APIs are excellent for experimentation, debugging, and are universally supported by all mainstream languages without requiring code generation.

### Modern RPC (gRPC, Finagle)
The new generation of RPC frameworks has accepted the flaws of location transparency and makes network requests explicit.
- **The Fix:** They use **Futures (Promises)** to encapsulate asynchronous actions that might fail, and support **Streams** (like gRPC) instead of just one-off request/response cycles.
- **The Deployment Rule:** REST is the predominant style for public APIs across organizational boundaries. RPC is strictly focused on high-performance requests between internal services owned by the same organization, usually within the same datacenter.

### API Evolution & Versioning
Evolution in services is brutal because cross-organizational API providers have no control over their clients and **cannot force them to upgrade**.
- Compatibility must often be maintained indefinitely, or the provider must maintain multiple versions of the API side-by-side. 
- There is no universal standard for API versioning (REST typically puts the version number in the URL or the HTTP Accept header).

## 3. Message-Passing Dataflow (Asynchronous Brokers)
Instead of a direct network connection, processes send messages through an intermediary called a **Message Broker** (e.g., Kafka, RabbitMQ). The communication is ***one-way and asynchronous*** (the sender drops the message and forgets about it; it does not wait for a response).

### Why use a Broker instead of direct RPC?
1. **The Buffer:** It absorbs traffic spikes, acting as a buffer if the recipient is overloaded or temporarily unavailable.
2. **Crash Recovery:** It automatically redelivers messages to processes that have crashed, preventing data loss.
3. **Decoupling:** The sender doesn't need to know the IP address or port of the recipient. It just publishes to a named **Queue** or **Topic**.
4. **Broadcasting:** A single message can be easily delivered to multiple subscribers simultaneously.

### Distributed Actor Frameworks

**The Threading Problem:** Traditional concurrency in a single process relies on threads. Threads share memory, which causes race conditions. Fixing race conditions requires "locks", which cause deadlocks and slow down the CPU.

**The Actor Model Solution:** Logic is encapsulated into independent entities called **Actors**. 
1. An actor has its own local, private state that no other actor is allowed to touch. 
2. They communicate exclusively by sending asynchronous messages to each other's "mailboxes."
3. An actor processes its mailbox **strictly one message at a time**. Because there is no simultaneous processing, you completely eliminate threads, locks, and race conditions.

**Distributed Actors:** Frameworks use this exact model to scale across multiple server nodes. The framework transparently takes an actor's message, encodes it into bytes, sends it over the network, and decodes it for an actor on another machine. *(Note: Because messages are now crossing a network, you still have to worry about forward/backward compatibility of the encodings during rolling upgrades!)*
