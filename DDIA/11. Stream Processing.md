# Stream Processing
Batch processing assumes that the input is *bounded*—it is of a known, finite size, allowing the job to know exactly when it has finished reading. 
* **The Reality of Unbounded Data:** In reality, a lot of data is *unbounded* because it arrives gradually over time. Because the dataset is never truly "complete," running daily batch jobs creates a built-in delay (changes are only reflected a day later).
* **The Solution:** Stream processing abandons fixed time slices entirely and simply processes every event exactly as it happens.

# Transmitting Event Streams
In a stream processing context, a record is known as an *event*. 
* **Event Definition:** A small, self-contained, immutable object containing the details of something that happened at some point in time. 
* **Producers and Consumers:** An event is generated once by a *producer* (publisher) and then potentially processed by multiple *consumers* (subscribers). Related events are grouped together into a *topic* or *stream*.

# Messaging Systems
When moving toward continual processing with low delays, periodically polling a database for new events becomes too expensive. Instead, it is better for consumers to be notified when new events appear via a messaging system.
* **Direct Messaging:** Some systems use direct network communication (like UDP multicast, ZeroMQ, or Webhooks) without intermediary nodes. However, these generally require producers and consumers to be constantly online. 
    * *`NOTE` (The Danger of Producer Crashes):* If a consumer drops offline, some direct protocols allow the *producer* to buffer the messages locally in memory and retry later. However, because there is no independent, durable broker in the middle, if the *producer* crashes before successfully delivering them, its local buffer is destroyed and all those pending messages are permanently lost.
* **Message Brokers (Message Queues):** A widely used alternative that acts as a database optimized for handling message streams. By centralizing data in the broker, it easily tolerates producers and consumers that connect, disconnect, and crash, because the question of durability is moved to the broker.
    * *`NOTE` (Durability Configuration):* Some traditional message brokers only keep messages in memory to maximize speed, while others (depending on configuration) write them to disk so they are not lost if the broker itself crashes. 
    * *`NOTE` (The Kafka Exception):* This "memory-first" configuration applies to traditional brokers (like RabbitMQ). Log-based brokers (like Kafka) are fundamentally different: they write *every single message* to an append-only log on disk by default, relying on sequential I/O and the OS page cache to maintain high throughput.

## Message Brokers vs. Databases
* **Deletion:** Databases keep data until explicitly deleted, whereas most traditional message brokers automatically delete a message when it has been successfully delivered.
* **Working Set:** Brokers assume their working set is fairly small (short queues). If consumers are slow and the broker must spill messages to disk, overall throughput degrades.
* **Queries vs. Notifications:** Databases return point-in-time snapshots to queries. Brokers do not support arbitrary queries, but actively notify clients when data changes.

## Multiple Consumers (AMQP / JMS Patterns)
When multiple consumers read from the same topic, two main patterns are used:
1. **Load Balancing:** Each message is delivered to exactly *one* of the consumers, sharing the work of processing the topic. (Useful when messages are computationally expensive and you need to parallelize the work).
2. **Fan-out:** Each message is delivered to *all* of the consumers. (Useful when multiple independent downstream systems need to react to the exact same event).
3. **The Combined Approach (Consumer Groups):** In robust systems, these patterns are combined. You *fan-out* the message to separate logical groups (e.g., the Search group, the Analytics group, the Email group). However, *within* each group, you *load balance* across multiple concurrent nodes (e.g., Search Node 1 and Search Node 2) so they can process independent messages simultaneously without duplicating work.

* **Acknowledgments:** To ensure messages aren't lost if a consumer crashes mid-processing, clients must explicitly tell the broker when they finish processing a message so it can be safely removed.
* **The Reordering Problem:** If you combine load-balancing with redelivery (Search Node 1 crashes, so its message is handed to Search Node 2), it inevitably leads to messages being processed out of order.

# Partitioned Logs (Log-Based Message Brokers)
Traditional messaging (JMS/AMQP) is destructive—receiving a message deletes it. Log-based message brokers (like Apache Kafka and Amazon Kinesis) were created to combine the durable storage approach of databases with the low-latency notifications of messaging.
## How Logs Work
* **Structure:** A producer appends a message to the end of the log, and a consumer receives messages by reading the log sequentially. 
* **Partitions:** To scale to higher throughput, the log is partitioned across different machines. Within each partition, the broker assigns a strictly ordered, monotonically increasing sequence number (an *offset*) to every message.
* **Fan-out is Trivial:** Several consumers can independently read the log without affecting each other, because reading a message does not delete it.

## Design Decision: Traditional vs. Log-Based
Log-based systems use *coarse-grained* load balancing: an entire partition is assigned to exactly one consumer node (it cannot be shared across multiple nodes), and it reads sequentially. This leads to a critical architectural choice:
* **Use Traditional (JMS/AMQP RabbitMQ) When:** Messages are expensive/slow to process, you need to parallelize on a message-by-message basis across many workers, and absolute ordering does not matter.
* **Use Log-Based (Kafka) When:** You have high message throughput, processing is fast, and strict message ordering is critical. 
    * *`NOTE` (The Head-of-Line Blocking Problem):* If processing a message takes 10 minutes, a log-based system forces the entire partition to wait. Traditional systems allow Consumer B to process message #2 while Consumer A is still stuck on message #1, maximizing concurrency at the cost of ordering.
    * *`NOTE` (The Parallelism Hack):* While it is technically possible to hack a partition to share work (e.g., having node A read even offsets and node B read odd offsets, or fanning out messages to a local thread pool), this is highly discouraged in practice. It completely ruins the lightweight simplicity of consumer offset management. If you need more parallelism in a log-based system, the correct architectural answer is to simply create more partitions.

## Consumer Offsets & Bookkeeping
Consuming a partition sequentially makes it incredibly easy to track which messages have been processed: all messages with an offset less than the current offset have been processed, and everything greater has not.
* **Massive Throughput Gains:** Because the broker doesn't need to track individual acknowledgments for every single message, the bookkeeping overhead is drastically reduced. This allows for aggressive batching and pipelining, heavily increasing the throughput of log-based systems.

## Disk Space Usage (The Circular Buffer)
If you only ever append to a log, you will eventually run out of disk space. To reclaim space, the log is divided into segments, and older segments are periodically deleted or moved to archive storage.
* **The Giant Ring Buffer:** Effectively, the log implements a bounded-size buffer (a circular buffer or ring buffer). However, because this buffer is on disk rather than in RAM, it can be massive.
* **`EXAMPLE` (Back-of-the-Envelope Calculation):** If a typical large hard drive has a capacity of 6 TB and a sequential write throughput of 150 MB/s, it would take about 11 hours to fill the drive if you are writing messages at the absolute fastest possible rate. 
    * *The Reality:* Thus, the disk can buffer a *minimum* of 11 hours of messages before overwriting. Because real-world deployments rarely max out the disk's write bandwidth constantly, a typical log can easily buffer several days' or even weeks' worth of messages.
* **Constant Throughput:** Regardless of how long you retain messages, the throughput of a log remains completely constant because every message is written to disk anyway. 
    * *`NOTE` (The Traditional Broker Contrast):* Traditional messaging systems keep messages in memory by default. They are fast when queues are short, but their throughput completely crashes when queues get too large and they are forced to frantically spill messages to disk.

## When Consumers Cannot Keep Up
Systems typically handle slow consumers in three ways: dropping messages, buffering, or applying backpressure. The log-based approach is essentially **buffering** with a massive, fixed-size disk buffer.
* **Dropping Old Data:** If a consumer falls so far behind that it requests messages older than what the log has retained on disk, it will simply not be able to read them. The broker effectively drops those old messages.
* **Operational Isolation (The Big Advantage):** Even if a consumer falls dangerously behind and starts missing messages, *only that specific consumer is affected*. It does not disrupt the broker or any other active consumers. You can experimentally consume a production log for debugging without fear of taking down the system.
* **The Traditional Broker Danger:** This heavily contrasts with traditional message brokers. In AMQP systems, if a consumer crashes and you forget to explicitly delete its queue, the broker will stubbornly accumulate messages for it forever, eventually draining the system's RAM and starving the active consumers.

## Replaying Old Messages (The Batch Connection)
In AMQP/JMS-style brokers, acknowledging a message is a destructive operation—it deletes the message from the broker. You cannot run the same consumer again and expect the same result.
* **Read-Only Processing:** In a log-based broker, consuming a message is more like reading a file. It is a strictly read-only operation that does not alter the log. 
* **The Offset "Side Effect":** The *only* side effect of processing a message on the broker itself is that the consumer's offset moves forward. 
* **Repeatable Experimentation:** Because the offset is entirely under the consumer's control, you can deliberately reset a consumer's offset to yesterday and point its output to a new location. This allows you to reprocess historical data safely.
* **Convergence with Batch Processing:** This non-destructive replay ability makes log-based messaging function exactly like the *batch processes* (where derived data is built through repeatable, read-only transformations), combining the safety of batch with the low latency of streams.

# Databases and Streams
The connection between databases and streams runs deeper than just the physical storage of logs on disk. 
* **The Replication Log is a Stream:** A replication log is simply a stream of database write events produced by a leader as it processes transactions. The followers applying that stream of writes to their own copy of the database is essentially just stream processing.
* **State Machine Replication:** If every event represents a write, and every replica processes the same events in the same order, all replicas end up in the exact same final state.
## Keeping Systems in Sync
There is no single system that can satisfy all data storage, querying, and processing needs. A modern architecture typically combines an OLTP database for user requests, a cache for speed, a full-text index for search, and a data warehouse for analytics. 
* **The Challenge of Single-Source Storage:** Building one universal storage system is practically impossible because each component requires its own highly optimized, proprietary physical data structure (e.g., an LSM-Tree for the database, an inverted index for search, a column-oriented format for the warehouse).
* **The Synchronization Problem:** Because the underlying physical formats are vastly different across these heterogeneous systems, keeping the exact same data perfectly synchronized across all of them becomes the core architectural challenge.

### The Danger of Dual Writes
When data changes, a naive approach is to use *dual writes*, where the application code explicitly writes the data to the database, and then immediately writes it to the search index. This has serious fatal flaws:
* **Race Conditions:** If Client 1 sets `X=A` and Client 2 sets `X=B` concurrently, network delays can cause the database to see `A` then `B` (final value `B`), while the search index sees `B` then `A` (final value `A`). The two systems silently become permanently inconsistent.
* **Fault Tolerance (Partial Failures):** One write may succeed while the other fails. Ensuring both succeed or both fail requires expensive atomic commit protocols (like 2PC).

## Change Data Capture (CDC)
To solve the dual-write problem, you must designate exactly one system as the true leader. Change Data Capture (CDC) is the process of observing all data changes written to that database and extracting them into a stream so they can be replicated to other systems.
* **How it Works:** By parsing the database's internal replication log, CDC captures the changes and applies them to the search index in the *exact same order* they were written to the database. This entirely eliminates the race conditions of dual writes.
* **Implementations:** There are many tools built specifically for this log-parsing task. For example, Debezium and Maxwell parse MySQL binlogs, Bottled Water decodes PostgreSQL WALs, GoldenGate handles Oracle, and the broader Kafka Connect framework offers connectors for a wide variety of databases.
* **The Asynchronous Lag:** Like message brokers, CDC is usually asynchronous. The system of record database does not wait for the change to be applied to consumers before committing it.
* **The Downside (Stale Reads):** Because of this asynchronous design, a replication lag applies to the *derived data systems* (the consumers). If a user updates their profile in the system of record and immediately performs a search, the search index might temporarily return stale data because the CDC event has not yet been processed by the index.

### Initial Snapshots
If you are building a brand-new search index, applying a log of just *recent* changes is not enough, because the database deletes old logs to save disk space. You will be missing all the older historical data. 
* **Step 1: The Consistent Snapshot:** You must first take a consistent, point-in-time snapshot of the entire database. Crucially, you must record the exact log offset (the sequence number) at the exact millisecond this snapshot is taken.
* **Step 2: The Batch Load:** You then load this massive snapshot into the new search index. *(This is typically a heavy Batch Processing job like those in Chapter 10).* You dump the database, process it in chunks, and bulk-load it into the index. 
* **Step 3: The Stream Catch-Up:** While the batch job was running, live users were still changing data. Once the batch load finishes, the search index connects to the CDC stream and requests all changes starting from the *exact offset* recorded in Step 1, rapidly processing the backlog to catch up to real-time.

### How Debezium Handles Initial Snapshots
To avoid requiring custom batch-loading logic in the downstream application, modern CDC tools like Debezium "disguise" the massive initial snapshot as a normal stream of events:
* **The Traditional Snapshot:** Debezium locks the database briefly to record a consistent log offset, then executes a massive `SELECT *`. Every existing row is serialized into a synthetic CDC event (tagged as a "read") and published to the broker. 
    * *The Bottleneck:* This is an "all-or-nothing" operation. If the connector crashes during a massive, multi-hour snapshot, it must restart completely from scratch.
* **The Modern Solution (Incremental Snapshots):** To solve this bottleneck, modern CDC deployments chunk the initial snapshot by Primary Key. Debezium reads a small chunk, emits the events, and then pauses to process any new live streaming events, effectively interleaving the historical load with real-time updates.
* **The Interleaving Race Condition:** If a snapshot is chunked and interleaved, a dangerous race condition occurs: a fresh live update could arrive for a row just before the snapshot reads it. This would cause the connector to emit a fresh update followed by a stale read, breaking the strict ordering guarantee and corrupting downstream data.
* **The Solution (Watermarks and Reconciliation):** Debezium solves this using the *DBLog algorithm*. Before and after querying a snapshot chunk, it writes a "low watermark" and "high watermark" directly into the database's transaction log. 
    * *Preserving Order:* When Debezium reads the transaction log, it looks at the live updates that occurred between those two watermarks. If it sees a live update for a specific row inside the chunk window, it explicitly *discards* the stale snapshot read for that row. It relies entirely on the transaction log for that specific record, perfectly preserving the strict ordering guarantee.

### Log Compaction (The Perpetual Snapshot)
Keeping all CDC changes forever requires too much disk space. Log compaction solves this: the storage engine periodically looks for log records with the same key, throws away older duplicates, and keeps only the *most recent* update for each key.
* **The Topic is the Snapshot:** Because log compaction guarantees that the topic retains the absolute latest value for every single key, the log itself effectively becomes a perpetual, up-to-date snapshot of the database.
* **Bootstrapping New Systems:** This completely eliminates the need to ask the source database for a heavy, expensive snapshot. To build a brand-new derived data system (like a new search index), you simply start a consumer at offset 0 of the compacted log and sequentially scan to the end to obtain a full copy of the database contents.

## Event Sourcing
Event sourcing (from Domain-Driven Design) is similar to CDC in that it stores all changes to application state as a log of events. However, they operate at completely different levels of abstraction:
* **CDC (Low-Level):** The application uses the database normally (mutably). The CDC log is extracted under the hood at a low level.
* **Event Sourcing (Application-Level):** The application logic is explicitly built around immutable events. Updates and deletes are prohibited. Events reflect *intent* ("student cancelled course") rather than mechanics ("row deleted from table").

### Commands vs. Events
* **Commands:** When a user request arrives, it is initially a *command*. A command can fail (e.g., username is taken, seat is booked). 
* **Events:** The application validates the command synchronously. Once validated and accepted, it becomes an *event*. At the point an event is generated, it becomes an immutable *fact* that cannot be rejected by consumers.

### Deriving State from Events
Users want to see the current state of their cart, not an append-only log of changes. Therefore, event sourcing applications must deterministically transform the event log into current application state.
* **The Compaction Difference:** CDC events contain the entire new version of a record, making log compaction easy (just keep the latest event). Event sourcing events model intent and do not override prior events, meaning you generally need the full history to reconstruct the final state, so log compaction is not possible in the same way. 
* **Performance Optimization (Snapshots):** Because reprocessing the entire history of events from the beginning of time is incredibly slow, event-sourced applications typically store periodic snapshots of the current derived state. If a system crashes, it simply loads the most recent snapshot and only replays the events that occurred *after* that snapshot was taken.
* **The Log is Still the Source of Truth:** It is important to note that these snapshots are purely a performance optimization for faster reads and recovery. The core philosophy of event sourcing remains that the system durably stores all raw events forever and can reprocess the full log from scratch whenever required.

## State, Streams, and Immutability
Mutable state and an append-only log of immutable events are two sides of the same coin. The log of all changes (the changelog) represents the evolution of state over time.
* **The Mathematical Analogy:** Application state is what you get when you *integrate* an event stream over time. A change stream is what you get when you *differentiate* the state by time.
* **Databases are Caches:** Transaction logs record the actual changes. From this perspective, the database itself is simply a cache of the latest record values found in the logs.

## Advantages of Immutable Events
Immutability is a centuries-old concept, similar to financial accounting ledgers where transactions are strictly append-only.
* **The Audit Trail:** If a mistake is made, accountants do not erase the incorrect transaction; instead, they append a compensating transaction (like a refund) to correct the balance while preserving the audit trail.
* **Safe Recovery:** Beyond auditability, immutable append-only logs make it much easier to recover from buggy code, as destructive overwrites do not permanently corrupt the original source data.
* **Capturing Intent:** Immutable events capture intent and history that would otherwise be lost; for example, a customer adding and then removing an item from a shopping cart provides valuable analytics data that a mutable database would simply delete.

## Deriving Views and CQRS
By separating mutable state from the immutable event log, you can derive several different read-oriented representations from the exact same stream.
* **Command Query Responsibility Segregation (CQRS):** This approach grants immense flexibility by explicitly separating the form in which data is written from the form in which it is read.
* **The Schema Fallacy:** The traditional database design approach assumes that data must be written in the exact same form as it will be queried, which is a fallacy.
* **Embracing Denormalization:** With an event log acting as the source of truth, it is entirely reasonable to highly denormalize data in the read-optimized views, since the translation process safely manages the duplication and keeps it consistent.

## Concurrency Control
The primary downside of event sourcing and CDC is that consumers update read views asynchronously, meaning a user might make a write and immediately read a stale view that does not yet reflect their change.
* **Simplifying Writes:** However, deriving current state from an event log can actually simplify concurrency control: if the event is a self-contained description of a user action, it only requires a single atomic write to append to the log.
* **Single-Threaded Execution:** If the event log and the application state are partitioned in the exact same way, a single-threaded log consumer can process writes serially without needing any complex concurrency control mechanisms.

## Limitations of Immutability
Keeping an immutable history forever is not always feasible and depends heavily on the dataset's churn rate.
* **High Churn Degradation:** For workloads with a high rate of updates and deletes on a comparatively small dataset, an immutable history can grow prohibitively large, making the performance of log compaction and garbage collection critical for operational robustness.
* **The Deletion Mandate:** Legal and administrative frameworks (such as GDPR) frequently mandate that user data be truly deleted on demand, meaning an append-only "deleted" tombstone event is insufficient.
* **Rewriting History:** In these specific cases, systems must physically rewrite history to pretend the data was never written, a feature known in various systems as *excision* or *shunning*.
* **The Reality of Deletion:** Truly deleting data across storage engines, SSDs, filesystems, and backups is notoriously difficult, making deletion more a matter of making data impractically hard to retrieve rather than technically impossible.

# Processing Streams
Once you have a stream of events, you can process it using a piece of code known as an *operator* or a *job*. This is very similar to MapReduce jobs in batch processing, where a processor consumes input streams in a read-only fashion and writes output in an append-only fashion. 
* **The Crucial Difference from Batch:** A stream never ends (it is unbounded). Therefore, sorting does not make sense, and fault-tolerance mechanisms must change because restarting a stream job that has been running for years is not viable.

## Uses of Stream Processing
### Complex Event Processing (CEP)
CEP is geared toward searching for specific patterns of events within a stream. 
* **The "Complex" Event:** When the engine's state machine finds a sequence of simple events that match a specified pattern, it emits a single *complex event*. It is "complex" because it aggregates multiple simple underlying events into one higher-level, meaningful business event.
* **Database Role Reversal:** In a normal database, data is stored long-term and queries are transient. CEP reverses this: the *queries* (patterns) are stored long-term, and the *events* continuously flow past them.
* **`EXAMPLE` (Credit Card Fraud Detection):** 
    * **The Simple Events:** A stream of thousands of normal transactions flows into the system. For a specific user, three simple events occur: 1) A $1 purchase at a gas station in California. 2) A $500 electronics purchase 10 minutes later. 3) An ATM withdrawal in New York 5 minutes after that.
    * **Database Role Reversal (The Stored Query):** Instead of storing these transactions in a database and running a batch query at midnight to look for fraud, the bank stores a continuous query in the CEP engine: *"IF (Small Purchase) THEN (Large Purchase) THEN (Geographically Impossible Transaction) WITHIN 30 MINUTES."*
    * **The Complex Event:** As the live stream of simple transaction events flows past this stored query, the CEP engine's state machine connects the dots in real-time. It groups those three simple events together and emits a single, actionable complex event: **"Fraud Alert Triggered for Account #1234."**

### Stream Analytics
While CEP finds specific event sequences, stream analytics is oriented toward aggregations and statistical metrics over a large number of events (e.g., measuring event rates or calculating rolling averages).
* **Probabilistic Algorithms:** Stream analytics heavily rely on probabilistic algorithms like Bloom filters (for set membership) and HyperLogLog (for cardinality estimation). 
* **Approximation vs. Data Loss:** Probabilistic algorithms are merely a memory optimization designed to produce approximate statistical *results* (like a 99th percentile estimate) requiring significantly less RAM. 
* **Why Approximation is Not Data Loss:** The underlying stream events are *not* deleted, dropped, or lost—they still exist in full inside the event log. The approximation only happens at the *calculation layer* (the metric being computed, like an estimated unique visitor count), trading absolute mathematical precision for immense speed and memory efficiency.

### Maintaining Materialized Views
A stream of changes to a database can be used to keep derived data systems (caches, search indexes) up to date. This is a specific case of maintaining a materialized view.
* **The Infinite Window:** Unlike stream analytics (which look at a 5-minute window), building a materialized view potentially requires all events stretching all the way back to the beginning of time, relying on log compaction to discard obsolete events.

### Search on Streams
Search on Streams looks for *individual events* based on complex criteria, such as full-text search queries.
* **Real Estate Example:** A user asks to be notified when a new property matching their search criteria appears. 
* **Inverted Processing:** Like CEP, this turns processing on its head: the queries are stored, and the documents run past the queries. 

### Message Passing vs. Stream Processing (A Point of Contrast)
* **Why it's here:** This section contrasts traditional service-to-service communication (like RPC and Actor frameworks) with stream processing to clear up common confusion. 
* **RPC / Actors (Point-to-Point):** Uses ephemeral, 1-to-1 communication with arbitrary **cyclic** request/response patterns. 
* **Stream Processors (Dataflow):** Uses durable, multi-subscriber event logs with strict **acyclic** data pipelines. 
* **The Crossover (Distributed RPC):** Some stream engines (like Apache Storm) feature **Distributed RPC**. When a synchronous user request is inserted, the system wraps it in a unique ID and **injects it directly into the active event stream**. It flows through the stream processing nodes alongside background events, and once computed, the result unblocks and returns to the waiting client.
    * **`EXAMPLE` (Calculating Tweet Reach):** A user synchronously requests the reach of a trending URL (where **reach** is the total number of *unique* individuals who saw a post or link on their feed, as opposed to raw impressions). Instead of hitting a slow historical database, the DRPC system injects the URL as a transient event into the active stream. Parallel workers leverage the stream's pre-computed state and caches to aggregate the unique follower count on the fly, returning the result to the client in milliseconds without writing the request to the historical log.

# Reasoning About Time
In batch processing, dealing with time is easy because the process looks at the historical timestamps embedded in the events themselves. 
## Event Time vs. Processing Time
Many stream processing frameworks incorrectly use the local system clock on the processing machine (processing time) to define windows. 
* **The Danger of Processing Time:** Processing can be delayed by queueing, network faults, or restarts. If you measure the rate of requests based on processing time, a redeployed stream processor churning through a backlog will look like a massive, anomalous spike in traffic, when in fact the real rate of requests (event time) was perfectly steady.

## Knowing When You're Ready (Straggler Events)
If you group events by event time, you can never be entirely sure you have received *all* the events for a particular window, because a network interruption could delay some events. To handle these "straggler events," you can either:
1. **Ignore them:** Track dropped events as a metric and alert if the drop rate is significant.
2. **Publish a correction:** Output an updated value for the window and retract the previous output.

## Whose Clock Are You Using, Anyway?
Assigning timestamps is incredibly difficult when events are generated on a mobile app that might go offline and buffer events locally for days. The user's device clock cannot be trusted.
* **The 3-Timestamp Solution:** To adjust for incorrect device clocks, log three timestamps: 
	1) Time event occurred (device clock)
	2) Time event sent (device clock), and 
	3) Time event received (server clock). 
	By subtracting timestamp 2 from timestamp 3, you get the network/clock offset, which you can apply to timestamp 1 to estimate the true time the event occurred. Assuming, network delay is negligible and device clock offset doesn't change between time the event occurred and the time it was sent to the server.

## Types of Windows
Once you determine the event timestamp, you must define the time periods (windows) used for aggregation:

* **Tumbling Window:** 
  * Has a fixed length, and every event belongs to exactly one unique window. 
  * *Example:* 10:03:00 to 10:03:59, followed immediately by 10:04:00 to 10:04:59.
  * *Boundary Style:* Rigid, absolute clock boundaries.

* **Hopping Window:** 
  * Has a fixed length and a set interval ("hop"), but allows windows to overlap to provide smoothing. 
  * *Example:* A 5-minute window that hops forward every 1 minute (e.g., windows cover 10:00–10:05, 10:01–10:06, etc.). 
  * *Boundary Style:* Rigid clock-aligned grid. While you *can* technically offset a hopping window's start time to an odd second (like starting at 10:03:35), it will still evaluate all data against a rigid, pre-scheduled clock grid whether events happen to land there or not.

* **Sliding Window:** 
  * Contains all events that occur within a specific time interval of *each other*. 
  * *Example:* A 5-minute sliding window covering events from 10:03:39 to 10:08:12 because those specific events happen to fall within 5 minutes of one another.
  * *Boundary Style:* Dynamic and event-driven. Unlike hopping/tumbling windows that snap to hard clock boundaries, sliding windows do not use a fixed grid. Instead, they are implemented by maintaining a fluid buffer of events sorted by time, adding new events as they arrive and purging old ones when they expire.

* **Session Window:** 
  * Has no fixed duration or clock boundaries. 
  * *Behavior:* Groups together all events for the same user that occur closely in time, and automatically closes the window only after the user has been inactive for a specified period (e.g., 30 minutes of no activity).

# Stream Joins
* **Stream-stream join (window join):** 
  * *What it does:* Joins related events from two separate streams that occur within a specific time window.
  * *Example:* To calculate the click-through rate for a search feature, you must bring together search events and click events connected by the same session ID. The processor maintains state (e.g., indexing the last hour of events). If a search event expires without a matching click, you record that the search result was ignored.
	  * Note embedding search and click events together and sending them in single event will miss out on the cases where we did search and didn't click.

* **Stream-table join (stream enrichment):** 
  * *What it does:* Joins a continuous, unbounded stream of activity events against a changing database state, where the database changes are consumed as a background changelog stream.
  * *Example:* Augmenting a stream of user activity events with profile data. To avoid slow remote database lookups for every single event, the stream processor maintains a local replica kept continuously up to date via a Change Data Capture (CDC) stream.

* **Table-table join (materialized view maintenance):** 
  * *What it does:* Maintains a cached, read-optimized view of joined data by processing two separate changelog streams (e.g., matching users to their timelines) to keep a materialized view up to date.
  * *Example:* Maintaining a Twitter home timeline cache by joining a **tweets stream** and a **follows stream**. 
    * If **User A** posts a tweet ($u'$), it must be added to the timeline of *all current followers* ($v$). 
    * If **User B** follows User A ($v'$), *all existing tweets* from User A ($u$) must be added to User B's timeline. 
    * This mutual interaction is why the change stream of a materialized join beautifully mirrors calculus's product rule: $(u \cdot v)' = u'v + uv'$.

## Time-Dependence in Stream Joins
* **The Core Problem:** All three stream join types require the processor to maintain state from one stream and query it using messages from another. Because states change over time, *when* an event is processed relative to an update determines the outcome. If event ordering across different streams is undetermined, the join becomes **nondeterministic** (re-running the job won't guarantee the same result).
* **Real-World Example (Sales and Tax Rates):** If you join sales data with historical tax rates, a tax rate change might happen in the database. If a network delay causes the tax-update event to arrive *after* a sale event that occurred right around the same time, the stream processor might accidentally apply the new tax rate to an old sale (or vice versa), corrupting historical accuracy.
* **How Data Warehouses Solve It (Slowly Changing Dimensions):** 
  * They use **Slowly Changing Dimensions (SCD)** to achieve determinism.
  * Instead of mutating a record in place, every version of a record gets a **unique version identifier** (e.g., tagging an invoice with the exact tax rate version ID active at the literal minute of sale).
* **The Trade-off:** While versioning guarantees determinism, it breaks **log compaction**, because you are forced to permanently retain all historical versions of records rather than throwing away old ones.

# Fault Tolerance in Stream Processing

## The Challenge of Exactly-Once Semantics
* **Batch vs. Stream:** Batch processing achieves fault tolerance easily because input files are immutable; if a task fails, its partial output is discarded, and the task restarts from scratch, making it look like it ran *exactly once*. 
* **The Streaming Dilemma:** Stream processing runs continuously and outputs data indefinitely, meaning you cannot simply wait for a job to finish or discard all output when a failure happens. 

## Mechanisms for Fault Tolerance
To give the appearance of exactly-once processing despite component crashes, stream frameworks use specific recovery mechanisms:

* **Microbatching and Checkpointing:**
  * *Microbatching (e.g., Spark Streaming):* Breaks the stream into small blocks (typically ~1-second batches) and treats each like a mini-batch. 
    * **Implicit Processing-Time Windows:** Microbatching inherently creates tumbling windows based on processing time rather than event timestamps. 
    * **Carrying Over State Between Microbatches:** Because each microbatch is a separate mini-job, any data or window calculations that span across a larger time frame than a single microbatch cannot happen automatically. The application code must explicitly manage and carry over state from one microbatch to the next.
  * *Checkpointing (e.g., Apache Flink):* Periodically writes rolling snapshots of operator state to durable storage, triggered by barriers injected into the message stream without forcing a strict window size.
  * *The External Output Limitation:* Inside the stream processing framework, microbatching and checkpointing provide true "exactly-once" guarantees. However, **as soon as output leaves the system** (e.g., writing to an external database, sending an email, or firing a push notification), the framework can no longer discard the output of a failed task. If a task crashes right after sending an external message and restarts, the external side effect will happen a second time. Microbatching and checkpointing alone cannot prevent this; you need idempotence or atomic commits for external sinks.
* **Atomic Commits:**
  * To prevent side effects from going out of sync, database writes, state changes, operator outputs, and consumer offsets must happen **atomically** (all-or-nothing). 
  * Restricted streaming frameworks (like Google Cloud Dataflow, VoltDB, and Kafka) manage this internally without heavy distributed transaction protocols like XA by keeping state changes and messaging bound inside the framework.
  * The overhead of transaction protocol can be compensated by processing several inputs inside a single transaction.
* **Idempotence:**
  * Relying on idempotence implies several assumtions: restarting a failed task must replay the same message in same order, the processing must be deterministic, and no other node may concurrently update the same value.
  * If tasks fail, making operations idempotent allows safe retries. 
	  * Systems can achieve this by attaching metadata like a monotonically increasing Kafka message offset to updates so duplicates are automatically ignored. 
	  * Fencing may be required during failover to prevent a "zombie" node from concurrently modifying the same state.
## Rebuilding State After a Failure
Any stream process requiring state (windowed aggregations, counts, joins) must ensure that state can survive a crash. Three primary patterns achieve this:

1. **Remote Datastore Replication:** Keep state in a remote datastore and query it per message (though this can introduce high network latency).
2. **Local State Replication:** Keep state local to the stream processor for speed, but replicate it periodically (e.g., Flink writing snapshots to HDFS, or Kafka Streams replicating state via log-compaction topics).
3. **Replaying from Input Streams:** If the state consists of short window aggregations, you can entirely skip state replication and simply replay the input events corresponding to that short window from the log.
