# Integrating Disparate Systems
In non-trivial applications, integrating disparate systems is one of the most critical engineering tasks.
* **The Challenge:** This aspect of system-building involves integrating multiple different data systems—potentially with different data models and optimized for different access patterns—into one coherent application architecture.

## Systems of Record vs. Derived Data
On a high level, systems that store and process data can be grouped into two broad categories based on how they interact with the flow of information:
* **Systems of Record (Source of Truth):** This system holds the authoritative version of your data. When new data comes in (e.g., user input), it is first written here. Each fact is represented exactly once (normalized). If there is any discrepancy between another system and the system of record, the value in the system of record is, by definition, the correct one.
* **Derived Data Systems:** Data in these systems is the result of taking existing data from another system and transforming or processing it in some way. 
    * *Redundancy:* Technically, derived data is redundant; if you lose it, you can safely recreate it from the original source.
    * *Performance:* It is essential for getting good performance on read queries and is commonly denormalized. 
    * *Examples:* A cache is a classic example. Indexes, materialized views, and predictive summary data from usage logs also fall into this category.

# The Three Types of Data Systems
Data systems are generally distinguished into three different types based on timing, how they are triggered, and how their performance is measured:

* **Services (Online Systems):** A service waits for a request or instruction from a client to arrive. When received, the service tries to handle it as quickly as possible and sends a response back. 
    * *Primary Metric:* **Response time** is usually the primary measure of performance, and availability is often very important.
* **Batch Processing Systems (Offline Systems):** A batch processing system takes a large amount of input data, runs a job to process it, and produces some output data. Jobs often take a while (minutes to days), so there normally isn't a user waiting for them to finish. They are usually scheduled to run periodically.
    * *Primary Metric:* **Throughput** (the time it takes to crunch through an input dataset of a certain size).
    * *MapReduce:* This was a major step forward in terms of the scale of processing that could be achieved on commodity hardware. 
	    * MapReduce's importance is now declining because it aggressively writes intermediate state to disk after every step, causing massive I/O bottlenecks. Modern frameworks like Spark have largely replaced it by keeping intermediate data in memory.
* **Stream Processing Systems (Near-Real-Time / Nearline Systems):** Stream processing is somewhere between online and offline processing. A stream processor consumes inputs and produces outputs shortly after they happen, rather than operating on a fixed set of input data. This allows for much lower latency than equivalent batch systems.

# Batch Processing with Unix Tools
Long before modern distributed data systems, standard Unix tools established fundamental ideas for batch processing that carry over to large-scale, heterogeneous distributed systems today. 

Surprisingly many data analyses can be done in a few minutes using combinations of standard Unix tools (`awk`, `sed`, `grep`, `sort`, `uniq`, and `xargs`), and they perform surprisingly well.

## Sorting versus In-Memory Aggregation
When using tools to aggregate or group data (like counting web logs), you must manage how memory is utilized. This introduces the concept of the **working set**—the amount of memory to which the job needs random access (e.g., the number of *distinct* URLs).
* **The In-Memory Approach:** If the working set is small enough, keeping an in-memory hash table works fine, even on a laptop.
* **The Sorting Approach:** If the job's working set is larger than the available memory, the sorting approach has the massive advantage that it can make efficient use of disks.

### `NOTE`: How Large-Scale Sorting Works (External Merge Sort)
The GNU Coreutils `sort` utility automatically handles datasets larger than memory by spilling to disk and automatically parallelizing sorting across multiple CPU cores. 
* **The Algorithm (External Merge Sort / K-Way Merge):** To merge massive files without triggering an Out of Memory (OOM) error, the system does *not* load full files into RAM. Instead, it streams them.
* **Phase 1 (Sorting & Spilling):** Data is sorted in memory in chunks and written out to disk as individual, pre-sorted segment files.
* **Phase 2 (The Memory Buffer):** During the merge, the system allocates a tiny, page-sized **application memory buffer** (RAM) for each segment file. The OS reads sequential disk pages (e.g., 4KB blocks) into these buffers.
* **Phase 3 (The Min-Heap):** The algorithm pulls only the absolute smallest item from each buffer into an in-memory priority queue (a Min-Heap). It continually extracts the smallest item to the final output file, replacing it with the next single item from that specific buffer.
* **Refilling the Buffer:** When a memory buffer empties, the algorithm simply requests the next sequential disk page from that segment file. 
* **The Result:** This is the exact same principle used in SSTables and LSM-Trees. Because mergesort has sequential access patterns, it performs exceptionally well on disks. You can merge a massive dataset using just kilobytes of RAM, bottlenecked only by the sequential disk read speed.

## The Unix Philosophy
The ability to chain commands easily was a key design idea of Unix, described in 1978 as a set of design principles:
1. Make each program do one thing well. To do a new job, build afresh rather than complicate old programs by adding new "features".
2. Expect the output of every program to become the input to another, as yet unknown, program.
3. Design and build software to be tried early (rapid prototyping).
4. Use tools in preference to unskilled help to lighten a programming task, even if you have to detour to build the tools and expect to throw some of them out after you've finished using them.
    * *`NOTE`:* This means you should favour automation. Instead of paying someone (or wasting your own time) to manually do tedious, repetitive data work, take the time to write a custom script or build a small tool to automate it—even if you only use that tool once and throw it away right after.

## Composability and Interfaces
The true power of Unix tools (like `sort` or `awk`) is not just what they do individually, but how easily they can be composed together. This composability requires strict design principles.
* **A Uniform Interface:** If you want to connect *any* program's output to *any* program's input, all programs must use the exact same input/output interface. In Unix, that interface is a file (a sequence of bytes, often treated as ASCII text). 
    * *(Another example of a uniform interface is the URL. Before URLs, bulletin board systems (BBSs) required dialing specific phone numbers and configuring modems just to link to content, which killed interoperability).*
* **The Balkanization of Data:** Even databases with the exact same data model often lack a uniform interface to easily move data between them.
    * *`NOTE`:* This lack of integration leads to "Balkanization" (incompatible fragmentation). For example, even though PostgreSQL and MySQL both use the exact same relational data model, you cannot easily pipe the native contents of one directly into the other. Because of proprietary internal formats, you are forced to write custom glue code or use intermediate files (like CSVs) to translate between them.
* **Separation of Logic and Wiring:** Unix tools use standard input (`stdin`) and standard output (`stdout`). The program itself doesn't know or care where the data is coming from or going to. This is a form of *loose coupling* or *late binding*.
    * *`NOTE`:* If a program directly opens files for reading and writing, or starts another network connection, that I/O is wired up by the program itself. This reduces flexibility because you can no longer seamlessly pipe the output of another command into it using the shell (`|`).

# MapReduce and Distributed Filesystems
The biggest limitation of Unix tools is that they only run on a single machine. MapReduce is essentially the Unix philosophy distributed across potentially thousands of machines. 
* **Hadoop Distributed File System (HDFS):** While Unix tools use `stdin`/`stdout`, MapReduce jobs read and write files on a distributed filesystem (like HDFS or Amazon S3).
* **The Shared-Nothing Principle:** HDFS conceptually creates one massive filesystem using the attached disks of all conventional machines running the daemon. 
* **The NameNode:** A central server that keeps track of exactly which file blocks are stored on which machines.
* **Erasure Coding:** An alternative to standard replication (like Reed-Solomon codes) that allows lost data to be recovered with lower storage overhead. 
    * *`NOTE`:* Normally, MapReduce moves the computation to the exact machine where the file is stored to save network bandwidth (data locality). However, if you use erasure coding, a single file is broken into mathematical fragments spread across *multiple* machines. If you run a MapReduce job on erasure-coded data, you lose the locality advantage because the machine must fetch fragments over the network to rebuild the original file before processing it.

# MapReduce Job Execution
MapReduce is a programming framework where you write custom code to process large datasets. The framework automatically handles the complexities of moving data between machines.
* **The Framework's Role (Implicit Steps):** Step 1 (breaking files into records) is handled by the input format parser. Step 3 (sorting the keys) is completely implicit—the framework guarantees the data is sorted before giving it to the reducer. 
* **The Mapper:** The framework passes the input to the mapper to extract keys and values. 
    * *`NOTE`:* The mapper handles each record independently. It does not keep state from one record to the next, and it is perfectly fine if the keys are duplicates. For example, if it reads the text `"apple apple"`, the mapper can independently output `("apple", 1)` and then `("apple", 1)` again. The framework will group those duplicates together later.
* **The Reducer:** The framework collects all values belonging to the *same* key and calls the reducer with ***an iterator over that collection of values*** to process the sorted data.
    * *`EXAMPLE` (How Duplicates are Aggregated):* If independent mappers output the duplicate key `("apple", 1)` six different times across three different machines, the framework intercepts them, groups them, and calls the Reducer exactly *once* for that key: `Key: "apple", Values Iterator: [1, 1, 1, 1, 1, 1]`.
    * *`NOTE` (The Role of the Iterator):* The framework does *not* hand the Reducer a standard array of these values. If a "hot key" has 10 billion values, loading a 10-billion-item array would instantly crash the machine with an Out of Memory (OOM) error. Instead, the iterator acts as a streaming pipe. The custom reducer code simply writes a loop to stream and aggregate those values one by one directly from the local disk.
* **Scope of Processing (Mapper vs. Reducer):** 
    * **The Mapper:** Operates on exactly *one input record at a time*. The framework reads a block, parses it into records, and feeds them to the Mapper sequentially. The Mapper is completely stateless and unaware of other records or Mappers.
    * **The Reducer:** Operates on exactly *one globally unique key at a time*. The Reducer does not receive data directly from individual mappers. Instead, the framework's "Shuffle and Sort" phase intercepts all outputs from all mappers, merges identical keys together over the network, and calls the Reducer exactly *once* per unique key, passing it a single iterator containing all values generated by all mappers for that key.
* **Putting Computation Near Data:** The MapReduce scheduler tries to run each mapper on one of the machines that stores a replica of the input file. This saves copying the input file over the network, reducing network load and increasing locality.

## The Framework's Hidden Middle Layer (The Shuffle and Sort)
* **The System's Responsibility:** This entire phase happens *just after* the Mappers finish and *just before* the Reducers start. You (the developer) write zero code for this. The MapReduce framework automatically acts as a giant "mail-sorting" facility to bridge the gap between the two phases.
* **Code Distribution:** The framework first copies the application code (e.g., JAR files) to the appropriate machines before starting the map task.
* **Partitioning by Hash:** To ensure all key-value pairs with the exact same key end up at the exact same reducer, the framework partitions the map output based on a hash of the key. 
* **The Shuffle:** The entire process of partitioning by reducer, sorting, and copying data partitions from the mappers to the reducers over the network is known as the *shuffle*. (This is the exact mechanism that globally merges duplicate keys together).
* **Handling Massive Key Groups:** The reducer is finally called with a single key and an iterator that sequentially scans over all records with that same key.
    * *`NOTE`:* If a specific key (like a popular URL) has billions of values, those values cannot fit in RAM. The framework uses the iterator to stream the values directly from the massive file on the local disk, processing them one at a time.

## MapReduce Workflows
A single MapReduce job is limited (e.g., you need a second round of sorting to find the *most* popular URLs). Therefore, jobs are chained together into workflows.
* **Materialized State:** Unlike Unix pipelines that stream data in memory, MapReduce workflows are chained by writing intermediate state fully to the distributed filesystem (HDFS). The first job writes to a directory, and the second job reads from it.
* **Failure Handling:** A batch job's output is only considered valid when the job has completed successfully. If a job fails, MapReduce discards the partial output. A downstream job will not start until the prior job completes perfectly. 
* **Workflow Schedulers:** Because managing dependencies between complex chained MapReduce jobs is difficult, workflow schedulers like Oozie, Azkaban, Luigi, and Airflow are heavily utilized. Higher-level tools like Pig and Hive automatically wire these MapReduce stages together for you.

# Reduce-Side Joins and Grouping
* **Equi-Joins:** The most common type of join, where a record is associated with other records that have an identical value in a particular field (like a foreign key or document reference). 
* **The Index Problem:** If a database needs a few records, it uses an index. MapReduce has no concept of indexes—it performs a *full table scan* by reading the entire content of all files. 
* **The Batch Join Approach:** When doing analytic queries over large numbers of records, running millions of individual remote database queries over the network would overwhelm the database, ruin throughput, and introduce non-determinism. Batch jobs resolve joins by bringing a full copy of the database (via an ETL process) into the distributed filesystem and processing it simultaneously across machines.

## Sort-Merge Joins
* **The Process:** Mappers extract the join key (e.g., User ID). The MapReduce framework partitions and sorts the key-value pairs so that all activity events and the user record with the same user ID become adjacent to each other in the reducer input.
* **Secondary Sort:** To make joining efficient, the framework can arrange the records so that the reducer sees the "authoritative" database record *first*, followed by the stream of activity events in timestamp order. The reducer holds the single database record in a local variable and iterates over the events, never needing to make network requests.
    * *`EXAMPLE` (Secondary Sort in Action):* Imagine joining a User Database (containing birth dates) with a massive Activity Log (containing URLs visited) to see which age groups visit which pages. 
        * **The Mappers:** Both the Database Mapper and the Activity Mapper output the exact same key (e.g., `User_ID: 105`).
        * **The Framework:** Groups everything for `User 105` and uses a **Secondary Sort** to guarantee the authoritative database record lands at the very top of the list.
        * **The Reducer Input:** `Key: 105`, `Iterator: [ {DOB: 1971}, {URL: "/x"}, {URL: "/y"} ]`. 
        * **The Execution:** The Reducer calls `.next()` on the iterator just once, grabs the database record, and stores `DOB: 1971` in a local RAM variable. It then loops through the rest of the massive iterator, streaming the URL events one by one and combining them in memory to output `("/x", Age: 55)`—all without making a single external database query!
* **Separation of Concerns:** MapReduce cleanly separates the *physical network communication* (getting data to the right machine) from the *application logic* (processing the data once you have it). It completely shields application code from having to worry about partial failures or node crashes by transparently retrying failed tasks.

## Grouping and Handling Skew
* **Group By & Sessionization:** Grouping records by key is implemented using the exact same pattern as joins (bringing related data to the same place). 
    * *`NOTE`:* **Sessionization** is a common example. This means collating all scattered activity events for a particular user into a single continuous "session" to analyze their sequence of actions (e.g., for A/B testing).
* **Linchpin Objects & Hot Keys:** In many datasets, a few keys are disproportionately active (e.g., a celebrity with millions of followers on a social network). These are known as "hot keys" or "linchpin objects."
* **The Skew Problem:** Collecting all activity related to a hot key in a single reducer creates significant *skew*. That one reducer must process millions of records while the others finish quickly, delaying the entire downstream workflow.
* **Handling Skew:** 
    * **Skewed Joins (Pig):** Runs a *sampling job* first to proactively determine which keys are hot. Mappers then send records relating to a hot key to one of several random reducers (the other dataset must be replicated to all of those chosen reducers).
    * **Sharded Joins (Crunch):** Similar to Pig, but requires the hot keys to be specified explicitly rather than using a sampling job.

# Map-Side Joins
Reduce-side joins have the advantage of not making assumptions about the input data, but sorting, copying to reducers, and merging inputs is quite expensive. If your input data already meets strict layout assumptions, a **Map-Side Join** skips the reducer entirely. The mapper simply reads an input block and writes the final output.
* **Broadcast Hash Joins:** Used when a massive dataset is joined with a small dataset. 
    * The mapper loads the *entire* small dataset into an in-memory hash table, then streams through the massive dataset. 
    * Alternatively, it can store the small input in a read-only index on the local disk (leveraging the OS page cache for almost fast lookups as in-memory) to avoid requiring the entire dataset to fit in RAM.
* **Partitioned Hash Joins (Bucketed Map Joins):** 
    * *`NOTE`:* If both input datasets are already partitioned the exact same way (e.g., by the last digit of the User ID), the mapper does *not* need to broadcast the full database. It only loads the specific matching *partition* into its hash table. This drastically reduces the memory footprint compared to a Broadcast Join.
** **Map-Side Merge Joins:** If the input datasets are not only partitioned identically but also *sorted* by the same key, the mapper can perform the same sequential merging operation that would normally be done by a reducer, completely eliminating the need for an in-memory hash table.
    * *`NOTE` (How it works without a hash table):* Because both files are already sorted by the join key, the mapper uses the exact same logic as the "merge" phase of a Merge Sort. It opens a streaming pointer to both files and reads them sequentially, side-by-side (like zipping up a jacket). If the keys match, it joins them; if one key is smaller, it simply advances that file's pointer. This means the mapper only needs to hold a single record in RAM at any given time!
## MapReduce Workflows with Map-Side Joins
When the output of a MapReduce join is consumed by downstream jobs, the choice between a map-side and a reduce-side join drastically affects the physical structure of the output.
* **Reduce-Side Output Structure:** The output of a reduce-side join is always partitioned and sorted by the *join key*.
* **Map-Side Output Structure:** The output of a map-side join is partitioned and sorted in the exact same way as the *large input* dataset (because one map task is started for each file block of the large input, regardless of the join type). 
* **The Importance of Metadata:** Because map-side joins require strict assumptions about the physical layout of the data (size, sorting, and partitioning), simply knowing the file path is not enough. In the Hadoop ecosystem, this specific metadata about how datasets are partitioned is tracked and maintained using tools like HCatalog and the Hive metastore.

# The Output of Batch Workflows
Batch processing sits in a unique space. It is not transaction processing (OLTP), nor is it typically used for analytic queries that produce reports for managers (OLAP). 
* **The True Output:** While batch processing scans massive datasets like OLAP, its final output is rarely a human-readable report. Instead, it produces a functional artifact—such as a search index, machine learning model, or database—that is built offline to be queried later by an online system.

## Building Search Indexes & Key-Value Stores
* **Search Indexes:** If you need to perform a full-text search over a fixed set of documents, a massive batch process is a highly effective way of building the initial indexes (e.g., Lucene) from scratch. 
* **Machine Learning & Recommendations:** Batch processing is heavily used to train machine learning models and recommendation systems over massive datasets of historical data. 
    * *`NOTE` (Batch vs. CDC):* Batch processing is used for the heavy-lifting of *bootstrapping* the initial index or training the ML model. To keep these systems updated in real-time as new data arrives, architectures shift to Change Data Capture (CDC) and Stream Processing  to incrementally update these artifacts.

## The Danger of External Side Effects
* **The Bad Idea:** It might seem obvious to use a database client library directly within a mapper or reducer to write batch results straight to a live production database. This is a terrible idea. Making a network request for every single record is orders of magnitude slower than the normal throughput of a batch task, and the concurrent writes from thousands of parallel tasks will easily overwhelm the database.
* **Breaking the Guarantee:** MapReduce provides a clean all-or-nothing guarantee: if a job succeeds, the output is perfect; if it fails, no output is produced. However, writing to an external system produces externally visible side effects that cannot be hidden, exposing partially completed jobs to the rest of the system if a task crashes. 
* **The Solution:** A much better solution is to build a brand-new database *inside* the batch job and write it as files to the job's output directory in the distributed filesystem. These read-only files are then bulk-loaded into servers.
    * *`NOTE` ("Separation of concerns"):* By building the database files offline and bulk-loading them later, you separate the heavy computation (MapReduce) from the live serving (web application), preventing batch failures from ever impacting live users.

## Philosophy of Batch Process Outputs
Following the Unix philosophy, MapReduce jobs treat inputs as completely **immutable** and avoid external side effects (the previous output is completely replaced with the new output). This explicit dataflow yields massive maintainability advantages:
* **Human Fault Tolerance:** If you deploy a bug and corrupt the output, you haven't destroyed the source data. You can simply roll back the code and rerun the job, or point the system back to the previous output directory. (Databases with in-place read-write transactions cannot do this).
* **Agile Feature Development:** Because rolling back is so easy, this principle of *minimizing irreversibility* allows engineering teams to move much faster. They can test new features without the fear of causing permanent data corruption.
* **Safe Automatic Retries:** If a task crashes mid-execution due to a transient issue, the framework can blindly retry it on another machine. This automatic retry is *only* safe because inputs are read-only and partial outputs from failed tasks are safely discarded.
* **Multi-Purpose Inputs:** The exact same set of input files can be used by various different jobs simultaneously (e.g., one job building a search index, while another monitoring job calculates metrics to evaluate if the data has unexpected characteristics).
* **Separation of Logic and Wiring:** Just like Unix tools, MapReduce separates the application logic from the wiring (configuring the input and output directories). This separation of concerns allows different teams to reuse the same code for entirely different tasks.

# Comparing Hadoop to Distributed Databases
Massively Parallel Processing (MPP) databases were pioneers in parallel join algorithms long before the MapReduce paper was published. However, their design philosophies are fundamentally different. 
* **Core Difference:** MPP databases focus on parallel execution of analytic SQL queries, while Hadoop/HDFS provides something much more like a general-purpose operating system that can run arbitrary programs.

## Diversity of Storage & Processing
* **The Sushi Principle (Raw Data is Better):** MPP databases require careful up-front modeling before data can be imported into their proprietary storage format. Hadoop opened up the possibility of indiscriminately dumping data into HDFS as raw byte sequences, and only later figuring out how to process it. There may not be one ideal data model, so dumping data in its raw form allows for multiple different transformations later.

## Designing for Frequent Faults (MPP vs. MapReduce)
When comparing MapReduce to Massively Parallel Processing (MPP) databases, two major differences in design approach stand out: how they handle faults, and how they utilize memory and disk.

* **The Handling of Faults:**
    * **MPP Databases:** If a single node crashes while a query is executing, most MPP databases abort the *entire query* and force the user (or system) to restart it from scratch. 
    * **MapReduce:** Tolerates failures at the granularity of an *individual task*. If one mapper crashes, the framework just retries that one specific task on another machine without aborting or affecting the rest of the massive job.

* **The Use of Memory and Disk:**
    * **MPP Databases:** Prefer to keep as much data as possible in memory (e.g., using in-memory hash joins) to avoid the high cost of reading from disk. Because MPP queries usually finish in a few seconds or minutes, restarting an aborted query from scratch isn't a huge penalty.
    * **MapReduce:** Is incredibly eager to write data to disk. It does this partly assuming the dataset will never fit in RAM, but heavily for fault tolerance (creating checkpoints so individual tasks can be retried).

* **The Overhead Trade-off:** 
    * Because MapReduce constantly writes intermediate state to disk to enable these task-level retries, it incurs significant overhead. This makes it inherently slower than an in-memory MPP database during a "perfect," fault-free run. 
    * However, for massive batch jobs that take hours or days to complete, this overhead is a necessary tax—restarting a 48-hour job from scratch just because a single node blinked offline is unacceptable.

* **Why Optimize for Faults?:**
    * MapReduce was designed for environments like Google, where a non-production batch task runs at a low priority and has a 5% risk of being preemptively terminated to make space for a higher-priority process. 
    * The framework is explicitly designed to tolerate frequent, unexpected task termination to allow the cluster to aggressively overcommit computing resources. In standard environments where tasks are not constantly being killed by the system, these heavy disk-writing MapReduce design decisions make much less sense.

# Beyond MapReduce (Dataflow Engines)
While robust, MapReduce's execution model suffers from poor performance for certain kinds of processing due to its reliance on fully materializing intermediate state.
* **The Downside of Materialization:** 
	* MapReduce writes out intermediate state to files on HDFS. Because of this, a MapReduce job can only start when *all* tasks in the preceding jobs have completed. Having to wait for a few slow "straggler" tasks grinds the entire workflow to a halt. 
	* Furthermore, mappers are often redundant, and replicating temporary intermediate state across several HDFS nodes is overkill.
## Dataflow Engines (Spark, Tez, Flink)
To fix these problems, dataflow engines like Spark, Tez, and Flink were developed. They handle an entire workflow as one job, rather than breaking it up into independent subjobs.
* **Operators:** Unlike MapReduce, functions do not take the strict roles of map and reduce; they are assembled in flexible ways and are called *operators*.
* **Performance Advantages:**
    * **Targeted Sorting:** Expensive work like sorting is only performed in places where it is actually required, rather than happening by default between every single stage.
    * **No Redundant Tasks:** There are no unnecessary map tasks (since work done by a mapper can often be incorporated into the preceding reduce operator).
    * **Locality Optimizations:** The scheduler can explicitly place the task that consumes data on the exact same machine as the task that produces it, exchanging data through a shared memory buffer rather than copying it over the network.
    * **Pipelined Execution:** Operators can start executing as soon as their input is ready; there is no need to wait for the entire preceding stage to finish.
    * **Reduced I/O (Memory/Local Disk):** Intermediate state between operators is kept in memory or written to the local disk, which requires drastically less I/O than writing it to HDFS (where it must be redundantly replicated across machines). 
    * **JVM Reuse:** Existing Java Virtual Machine (JVM) processes can be reused to run new operators, drastically reducing startup overheads compared to MapReduce (which stubbornly launches a brand-new JVM for every single task).

## Fault Tolerance in Dataflow Engines
* **Recomputation:** Spark, Flink, and Tez avoid writing intermediate state to HDFS. If a machine fails, the lost data is simply recomputed from other data that is still available (either a prior intermediary stage or the original input data).
    * *`NOTE` (When to Materialize Instead):* Recovering from faults by recomputing data is not always the right answer. If the computation is extremely CPU-intensive, or if the intermediate data is much smaller than the original source data, it is actually cheaper to just materialize that intermediate data to files rather than spending the compute to rebuild it from scratch.
* **Determinism Requirement:** When recomputing data, it is critical that operators are deterministic. If an operator produces different data on a retry, it creates contradictions for downstream operators, leading to cascading faults.
* **The Final Output:** When the job finally completes, its output still needs to go somewhere durable so users can find it, meaning final outputs are still written to HDFS. The massive improvement over MapReduce is simply saving yourself from writing all the *intermediate* state to the filesystem.

# Graphs and Iterative Processing
Batch processing is frequently used to perform offline analysis on entire graphs, such as running PageRank for web search or building recommendation engines.
* **The "DAG" Naming Confusion:** Dataflow engines (like Spark and Flink) arrange their *operators* in a Directed Acyclic Graph (DAG) to structure the flow of data. This is distinct from *graph processing*, where the data itself is structured as a graph of vertices and edges.
* **Iterative MapReduce:** Graph algorithms often traverse edges repeatedly until a metric converges or no edges remain. Because MapReduce only performs a single pass over data, running iterative algorithms requires an external scheduler to repeatedly trigger new MapReduce batch jobs.
    * *`EXAMPLE` (The Full-Scan Bottleneck):* Imagine finding reachable nodes in a graph of depth 3 (`A → B → C → D`). 
        * **Job 1:** Reads the *entire* graph, Node A passes a message to Node B, writes the *entire* graph to HDFS.
        * **Job 2:** Reads the *entire* graph again, Node B passes a message to Node C, writes the *entire* graph to HDFS.
    * *`NOTE` (The Core Inefficiency):* MapReduce relies on full dataset scans and is entirely stateless. Even if only a tiny fraction of the nodes actually need to process changes during an iteration, MapReduce forces you to read, process, and rewrite 100% of the graph to disk every single time.
## The Pregel Processing Model
To optimize graph processing, the *bulk synchronous parallel* (BSP) model became popular, heavily driven by Google's Pregel paper. 
* **Vertex State:** In Pregel, one vertex "sends a message" to another vertex along an edge. The massive difference from MapReduce is that a vertex *remembers its state in memory* from one iteration to the next. The function only needs to process brand-new incoming messages, drastically reducing unnecessary work.
* **Exactly-Once Fault Tolerance:** Pregel implementations guarantee that messages are processed exactly once at their destination vertex in the following iteration. This fault tolerance is achieved by periodically checkpointing the full in-memory state of all vertices to durable storage at the end of an iteration. If a node fails, the system rolls back to the last checkpoint.
* **Partitioning Overhead:** In practice, graphs are often partitioned arbitrarily by vertex ID, making no attempt to group related vertices onto the same machine. This results in massive cross-machine network communication overhead. 
* **Single-Machine Preference:** Because of this immense network overhead, it is highly recommended *not* to partition a graph across a distributed cluster unless absolutely necessary. If a graph can fit in the memory (or even on the local disks) of a single computer, a single-machine algorithm will likely heavily outperform a distributed batch process like Pregel.

# High-Level APIs and Declarative Languages
Programming pure MapReduce jobs by hand is notoriously laborious. Over time, high-level languages and dataflow APIs (like Hive, Pig, Spark, and Flink) emerged to simplify this.
* **Interactive Development:** Besides requiring less code, these high-level interfaces allow for interactive use. Developers can write analysis code incrementally in a shell and run it frequently to experiment with the dataset, leaning heavily into the Unix philosophy of rapid prototyping.
* **Query Optimizers:** Specifying operations (like joins) in a declarative way allows the framework to analyze the inputs and automatically decide which join algorithm (e.g., Broadcast Hash vs. Sort-Merge) is most optimal for the task at hand.
* **Vectorized Execution:** By incorporating declarative elements for simple filtering and mapping, optimizers can utilize column-oriented storage and vectorized execution. This iterates over data in tight inner loops that are friendly to CPU caches and completely avoids the CPU overhead of making arbitrary function calls for every single record.
* **Convergence with MPP:** By adding declarative query optimizers to their high-level APIs, batch processing frameworks have begun to look—and perform—much more like traditional Massively Parallel Processing (MPP) databases, while retaining their unique flexibility to run arbitrary code.
