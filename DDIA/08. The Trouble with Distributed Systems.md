- **The Core Assumption:** To understand distributed systems, we must turn our pessimism to the maximum and assume that anything that *can* go wrong *will* go wrong. 
* **The Engineer's Mindset:** In distributed systems, suspicion, pessimism, and paranoia pay off. 
# Faults vs. Partial Failures
* **Single Computer (Internal Fault):** A deliberate design choice in computers dictates that if an internal hardware fault occurs, the computer prefers to crash completely rather than return a wrong result (because wrong results are confusing). It is deterministic: it either fully works or is entirely broken. 
* **Distributed System (Partial Failure):** In a distributed system, some parts may break in unpredictable ways while other parts continue working perfectly. These partial failures are nondeterministic.
* **The Goal:** If we want distributed systems to work, we must accept the possibility of partial failure and build a reliable system from unreliable components.
* **Scale Doesn't Matter:** Even in smaller systems with only a few nodes, it is important to think about partial failure.
* **The Supercomputer Contrast:** High-performance computing (HPC) handles faults differently. If one node fails, the entire cluster workload is stopped, repaired, and restarted from the last checkpoint. Cloud computing and enterprise datacenters cannot do this; they must handle faults without stopping the whole system.
## The Limit of Reliability
* A system can be more reliable than its underlying parts, but there is always a limit.
* ***Example:*** TCP can hide packet loss, duplication, and reordering from the application, but it cannot magically remove delays in the network.
* **The Value of Imperfect Abstractions:** Even though higher-level systems (like TCP) cannot achieve perfect reliability, they are still incredibly useful because they hide tricky low-level faults. This abstraction frees the application engineer to focus on reasoning about and handling a much smaller, more manageable set of high-level faults.
# Unreliable Networks
Most internet services are built on shared-nothing systems (independent machines connected by a network). These are asynchronous packet networks that give no guarantees about when a message will arrive, or if it will arrive at all.
## The 6 Things That Can Go Wrong
If you don't get a response back its *impossible* to tell why. Usually this is handled with *timeout*. If you send a request and expect a response, the following can occur:
1. Your request may have been lost (unplugged cable)
2. Your request may be waiting in a queue to be delivered later(overloaded network/recipient)
3. The remote node may have failed (crashed or powered down)
4. The remote node may have temporarily stopped responding but will recover later(stop the world garbage collection pause)
5. The remote node processed the request, but the response was lost on the network(misconfigured network switch improperly dropping or misdirecting the return packets)
6. The remote node processed the request, but the response was delayed(overloaded recipient network)

## Network Faults in Practice
* **The Reality of Faults:** Public cloud services (like EC2) are notorious for transient network glitches, but even well-managed private datacenters experience them (e.g., switch upgrades delaying packets for over a minute, or sharks biting cables). 
* **Directionality:** Just because a network link works in one direction doesn't guarantee it works in the opposite direction.
* **Network Partitions:** When a network fault cuts off one part of the network from the rest, it is called a network partition or netsplit.

## Handling vs. Tolerating Network Faults
Because network faults *can* occur, your software needs to be able to handle them. However, handling a fault is not the equivalent of tolerating it:
* **Handling a Fault:** The system gracefully manages the error without crashing or corrupting data, but the user's workflow is still interrupted. For example, if the network drops, simply showing an error message to the user is valid *handling*. 
* **Tolerating a Fault:** The system completely masks the failure so the user never even notices it happened. The system seamlessly works around the issue (e.g., automatically retrying a different server) without interrupting the user's workflow.
# Detecting Faults
Because you cannot know *why* a response didn't arrive, detecting faults is incredibly difficult. You are generally dealing with two scenarios:
## Rapid Feedback vs. Timeouts
* **Rapid Feedback (Explicit Failure):** You get an immediate notification that something is wrong. 
    * *Example:* You try to connect to a node, but no process is listening on the destination port. The remote operating system immediately sends back a packet to refuse the TCP connection.
    * *The Catch:* You can't rely on this. Even if the network layer (TCP) acknowledges that the packet was delivered successfully, the application itself might crash before it actually processes the data. To be completely sure a request succeeded, you must have a positive response from the application itself.
* **No Response (Implicit Failure):** In most cases, if something goes wrong, you get no feedback at all. 
    * *Example:* You send a request, a congested network switch drops the packet, and you just sit there waiting in silence. 
    * *The Solution:* You must rely on timeouts. The standard approach is to retry a few times (often transparently via TCP), wait for a specific timeout period to elapse, and if you hear nothing back, eventually declare the node dead.

## Timeouts and Unbounded Delays
If a timeout is the only sure way of detecting a fault, how long should it be?
* **Long Timeout:** Users have to wait a long time before seeing an error message.
* **Short Timeout:** Detects faults faster, but carries a high risk of incorrectly declaring a node dead when it was only suffering a temporary slowdown. 
* **The Cascading Risk:** When a node is declared dead, its responsibilities are transferred to other nodes, placing additional load on the network. Prematurely declaring nodes dead can overload the remaining nodes, causing a cascading failure.
* **The Problem with Asynchronous Networks:** They have *unbounded delays*—there is no upper limit on the time it may take for a packet to arrive, and hence servers cannot guarantee they will handle requests within a maximum time.

## Why Delays Happen (Queueing)
The variability of packet delays is most often due to queueing.
* Network switches must queue up packets if multiple nodes send data to the same destination simultaneously.
* Operating systems queue incoming requests if all CPU cores are busy.
* Virtual machine monitors queue data when the guest OS is temporarily paused.
* TCP flow control (backpressure) artificially limits the sending rate, adding additional queueing at the sender before data even enters the network.
* A "noisy neighbor" (another customer sharing the multi-tenant datacenter resources) can cause highly variable network delays.

* **Dynamic Timeouts:** Rather than using constant timeouts, modern systems continually measure response times and jitter to automatically adjust timeouts (e.g., using a Phi Accrual failure detector).


### The BGP Exception: Circuit Switching at the Macro Level
While the internet generally relies on packet switching (which causes unpredictable delays), there is a notable exception at the highest levels of internet infrastructure. 

* **Peering Agreements & BGP:** Core Internet Service Providers (ISPs) connect to each other and establish global routes using the Border Gateway Protocol (BGP). 
* **Resemblance to Circuit Switching:** Unlike standard IP routing which dynamically fights for bandwidth, these top-level peering agreements bear a closer resemblance to *circuit switching*. At this macro level, organizations actually *can* buy dedicated, guaranteed bandwidth.
* **Why it Doesn't Solve Application-Level Delays:** Even though dedicated bandwidth exists here, it doesn't solve the unbounded delay problem for application developers due to two major limitations:
    * **Network-Level, Not Host-Level:** BGP operates at the level of *entire networks* communicating with other networks. It cannot be used to establish a dedicated, guaranteed circuit between two individual hosts (e.g., your specific database server and a client's laptop).
    * **Timescale:** BGP route establishment operates on a very long timescale. It is meant for long-term infrastructural agreements, not for spinning up dynamic, short-lived connections on the fly for bursty web traffic.
# Synchronous vs. Asynchronous Networks
* **Circuit-Switched (Synchronous):** Similar to traditional telephone networks. When a connection is made, it establishes a dedicated circuit with a fixed, guaranteed amount of bandwidth allocated along the entire route. Because the space is reserved, data does not suffer from queueing, resulting in a **bounded delay**. 
* **Packet-Switched (Asynchronous):** Similar to Ethernet and IP datacenter networks. They do not reserve space in advance. Instead, they opportunistically use whatever network bandwidth is available at that exact moment. Because of this dynamic sharing, they suffer from queueing and **unbounded delays**. 

## Why Use Packet Switching?
Datacenter networks and the internet use packet switching because they are optimized for **bursty traffic** (like web pages or file transfers) rather than constant data streams (like audio/video phone calls).
* **The Bandwidth Allocation Problem:** If you tried to use a static circuit to transfer a bursty file, you would have to guess the bandwidth allocation. 
	* If you guess too low, the transfer is unnecessarily slow and leaves available network capacity unused. 
	* If you guess too high, the network will simply reject the connection because it cannot guarantee that massive amount of bandwidth for the entire duration. 
	* TCP avoids this by dynamically adapting its transfer rate to whatever network capacity is currently available.
* **The Latency/Utilization Trade-Off:** Variable delays in networks are not a law of nature; they are a cost/benefit trade-off. Packet switching relies on dynamic resource partitioning. This maximizes wire utilization (making each byte cheaper to send) but causes unpredictable queueing delays. 
* **The Current Reality:** Because Quality of Service (QoS) guarantees are not currently enabled in multi-tenant clouds or the public internet, we must assume that network congestion, queueing, and unbounded delays *will* happen. Consequently, there are no magically "correct" timeouts—they must be determined experimentally.

# Unreliable Clocks
Clocks in a distributed system are used to answer two fundamental types of questions:
1. **Measuring Durations:** (e.g., the time interval between a request being sent and a response being received, or measuring timeouts).
2. **Describing Points in Time:** (e.g., events that occur on a particular date and time, like when an article was published).

* **The Hardware Reality:** Each machine on the network has its own clock, which is an actual hardware device—usually a quartz crystal oscillator. Because these devices are not perfectly accurate, every machine has its own slightly different notion of time (some run faster, some slower). 
* **Synchronization:** It is possible to synchronize clocks to some degree using the Network Time Protocol (NTP), which adjusts the computer's clock according to time reported by a group of servers (which get their time from highly accurate sources like GPS receivers).

## Time-of-Day Clocks vs. Monotonic Clocks
### Time-of-Day Clocks (Wall-Clock Time)
* **What they do:** They return the current date and time according to a calendar, typically representing the number of seconds (or milliseconds) since the epoch (midnight UTC on January 1, 1970).
* **The Danger:** Time-of-day clocks are usually synchronized with NTP. If the local clock gets too far ahead of the NTP server, it may be forcibly reset, causing the clock to appear to jump back to a previous point in time. These jumps make time-of-day clocks completely unsuitable for measuring elapsed time.
* **Leap Seconds:** (*adjustments due to earth's rotation.*) These adjustments result in a minute that is 59 or 61 seconds long, creating additional unexpected time jumps that can crash systems expecting a strict 60-second minute. A common mitigation is "smearing," where NTP servers intentionally lie and adjust the time gradually over the course of a day.
### Monotonic Clocks
* **What they do:** They are guaranteed to *always move forward* (unlike time-of-day clocks which can jump backward). 
* **Measuring Duration:** You check the value of the monotonic clock at one point, do something, and check it again. The difference between the two values tells you exactly how much time elapsed.
* **NTP's Role:** NTP cannot force a monotonic clock to jump forward or backward. Instead, it adjusts the frequency at which the monotonic clock moves forward (known as *slewing* the clock) if it detects the local quartz is moving faster or slower than the server.
* **Relationship to Wall-Clock Epoch:** A monotonic clock has absolutely no relationship to the wall-clock epoch (e.g., midnight Jan 1, 1970). The absolute value of a monotonic clock is completely meaningless; it might simply be the number of nanoseconds since that specific computer was booted. It makes no sense to compare monotonic clock values from two different computers because they do not share the same starting point.
* **Example in Java (`currentTimeMillis` vs `nanoTime`):** 
    * If you call the time-of-day clock, `System.currentTimeMillis()`, it returns a number tied to the 1970 epoch, such as `1784861234567` (which translates directly to a specific date and time on the calendar). 
    * If you simultaneously call the monotonic clock, `System.nanoTime()`, it returns an arbitrary, unrelated number like `3948571029384` (which might just mean the JVM started 3,948 seconds ago). The only valid way to use `nanoTime()` is to call it before a task, call it again after the task, and subtract the first arbitrary number from the second to find the elapsed duration.

## Clock Synchronization and Accuracy Pitfalls
Hardware clocks and NTP can be fickle beasts. Our methods for getting a clock to tell the correct time aren't as reliable or accurate as you might hope:
* **Drift:** Quartz clocks drift (run faster or slower than they should) depending on the machine's temperature. Even if synchronized every 30 seconds, a clock can drift by 6 ms; if synchronized once a day, it can drift by 17 seconds.
* **Forced Resets:** If a computer's clock differs too much from an NTP server, it may refuse to synchronize, or the local clock will be forcibly reset (causing large sudden jumps backward or forward).
* **Network Limits:** NTP synchronization can only be as good as the network delay; accuracy is severely limited on a congested network with variable packet delays.
* **Rogue Servers & Firewalls:** NTP servers can be wrong/misconfigured, or a node might be accidentally firewalled off from NTP servers without anyone noticing.
* **Leap Seconds:** A minute with 59 or 61 seconds messes up timing assumptions in systems. The best way to handle this is for NTP servers to "lie" and perform the adjustment gradually over a day (known as *smearing*).
* **Virtual Machine Pauses:** In virtual machines, a shared CPU core might cause a VM to pause for tens of milliseconds. To the application, this pause manifests as the clock suddenly jumping forward.
* **Untrusted Devices:** You cannot trust the hardware clocks on mobile or embedded devices, as users often deliberately set them incorrectly.

### **The Cost of Extreme Accuracy:** 
- Is it actually necessary to invest heavily in near-perfect clock synchronization? 
	- For most standard applications, the answer is no; normal NTP synchronization is "good enough." Achieving extreme accuracy requires significant money and effort, such as deploying physical GPS receivers in every datacenter and using the Precision Time Protocol (PTP). Because of this high cost, it is usually only pursued for highly specialized systems, such as high-frequency trading platforms (to comply with MiFID II regulations for detecting market manipulation) or globally distributed databases like Google Spanner.
## Relying on Synchronized Clocks
If a piece of software is relying on an accurately synchronized clock, the result of a faulty clock is more likely to be silent and subtle data loss than a dramatic crash. 
* **The Rule:** If you use software that requires synchronized clocks, it is essential that you carefully monitor the clock offsets between all machines. Any node whose clock drifts too far from the others should be declared dead and removed from the cluster.
### Timestamps for Ordering Events (Last Write Wins)
Relying on time-of-day clocks to order events across multiple nodes (e.g., determining which client's write to a database happened first) is highly dangerous. The most common conflict resolution strategy that uses this is **Last Write Wins (LWW)**.

**Fundamental Problems with LWW:**
* **Silent Data Loss:** Database writes can mysteriously disappear because a node with a lagging clock cannot overwrite values previously written by a node with a fast clock (until the clock skew between nodes has elapsed).
    * *Example (Broken Increment Operations):* LWW breaks operations that require reading and updating a value. If Client A reads a counter at `1` and increments to `2` (Timestamp 10:05), and Client B concurrently reads `1` and increments to `2` (Timestamp 10:03 because B's clock is lagging), LWW simply compares the timestamps. It accepts A's write of `2` and discards B's write entirely. The counter ends at `2` instead of the correct `3`, meaning data is permanently lost.
* **False Concurrency:** LWW cannot distinguish between writes that occurred sequentially in quick succession and writes that were truly concurrent (where neither writer was aware of the other).
* **Tiebreakers:** It is possible for two nodes to independently generate writes with the exact same timestamp. An additional tiebreaker value (like a large random number) is required, which can lead to violations of causality. 
* **The Definition of "Recent":** Discarding data based on the most "recent" value depends entirely on a local time-of-day clock, which may well be incorrect.

### Physical vs. Logical Clocks
* **Physical Clocks (Time-of-Day and Monotonic):** Measure *actual elapsed time* (durations or specific points in time) using a physical hardware device like a quartz crystal.
* **Logical Clocks:** Do not measure elapsed time of day or seconds at all. They are simply incrementing counters (e.g., 1, 2, 3...) used solely to track the *relative ordering of events* (whether one event happened before or after another). Because they do not rely on quartz crystals or network synchronization, they are a much safer alternative for ordering events than physical clocks.

## Clock Readings Have a Confidence Interval
Because of quartz drift and network delays, a clock reading should not be thought of as a single point in time. It is more like a range of times, within a confidence interval.
* With an NTP server on the public internet, the best possible accuracy is tens of milliseconds, but the error may easily spike to over 100 ms during network congestion. 
* If you are getting time from a server, your uncertainty interval is based on expected quartz drift + NTP server uncertainty + network round-trip time.
### Spanner's TrueTime and The Commit Wait
Because clock readings are a range of uncertainty rather than a single point in time, ordering database transactions accurately across a global system is extremely difficult. 

* **The TrueTime API:** Instead of returning a single timestamp, Google's TrueTime explicitly reports the confidence interval as two values: `[earliest_possible_timestamp, latest_possible_timestamp]`.
* **Guaranteeing Causality (The Commit Wait):** To ensure that timestamps strictly reflect the true order of events (causality), Spanner assigns a transaction a timestamp at the end of its confidence interval, but **deliberately pauses and waits for the entire confidence interval to pass** before committing the read-write transaction.
* **Why it Waits:** If Spanner didn't wait, a subsequent transaction could be assigned a timestamp that overlaps with the previous one, making it look like the newer transaction happened first in the database history. By waiting until the first transaction's uncertainty window is entirely in the past, Spanner guarantees that any subsequent transaction will have a strictly higher timestamp. 
* **The Hardware Requirement:** Waiting adds latency to every single database write. To keep this mandatory wait time as short as possible, Google deploys expensive GPS receivers and atomic clocks in every datacenter. This extreme hardware keeps the clock uncertainty window tiny (under 7 milliseconds), meaning the database only has to pause for a few milliseconds per commit.

## Process Pauses
Nodes rely on local clocks to know if they hold a "lease" (authorization to act as the leader and accept writes). A node must periodically renew this lease before it expires. 

If a thread checks the time, verifies the lease is valid, and then proceeds to process a request, it assumes very little time passes between the check and the execution. However, a thread might be unpredictably paused for a long time right in the middle of this process. If paused long enough, the lease expires, another node takes over, but the original thread wakes up completely unaware of the pause and performs unsafe processing.

### 7 Reasons a Thread Might Pause Unpredictably
Is it crazy to assume that a thread might be paused for several seconds or even minutes? Unfortunately not. A node can be paused for the following reasons:

1. **Garbage Collection (GC):** "Stop-the-world" GC pauses in runtimes like the JVM occasionally stop all running threads. These pauses have sometimes been known to last for *several minutes*. 
2. **Virtual Machine Suspension:** In virtualized environments, a VM can be *suspended* (saving memory to disk) and *resumed* later. This is often used for *live migration* of VMs from one physical host to another without rebooting.
3. **Laptop Lids:** On end-user devices, execution is arbitrarily suspended when the user closes their laptop lid.
4. **Context Switching:** When the OS switches to another thread, or the hypervisor switches to a different VM, the running thread can be paused at *any arbitrary point in the code*(***e.g. any line in a function it can just pause and wait)***. If the machine is under heavy load (high "steal time"), it may take a long time to get CPU cycles again.
5. **Synchronous Disk I/O:** A thread may be paused waiting for a slow disk I/O operation to complete. This can happen surprisingly—like Java lazily loading a class file. 
6. **Page Faults (Swapping/Paging):**  If the OS is configured to allow swapping to disk, a simple memory access might trigger a "page fault" requiring a page to be loaded from disk to memory. The thread is paused during this slow I/O operation. If memory pressure is high, the OS spends all its time just swapping pages in and out (known as *thrashing*). Server machines often disable paging entirely to prevent this—it is better to kill a process to free up memory than risk thrashing.
7. **Accidental SIGSTOP:** A Unix process can be paused instantly by a `SIGSTOP` signal (e.g., an engineer accidentally hitting Ctrl-Z in a terminal). If the process is left paused forever, it is handled safely as a node crash. The danger occurs when the engineer realizes their mistake and resumes the process (`SIGCONT`). The process wakes up unaware of the elapsed time and acts as a "zombie leader," potentially writing conflicting data after the cluster has already elected a replacement.

**The Distributed Concurrency Trap:** 
When writing multi-threaded code on a *single machine*, we use tools like mutexes, semaphores, and atomic counters to make it thread-safe. These tools **do not** directly translate to distributed systems ***because there is no shared memory***—only messages sent over an unreliable network. 
* **The Core Rule:** A node in a distributed system must assume that its execution can be paused for a significant length of time at any point, even in the middle of a function. 

## Response Time Guarantees (Real-Time Systems)
Some software controls physical objects (aircraft, rockets, cars). In these environments, failing to respond within a specified time can cause the entire system to fail. 
* **Hard Real-Time Systems:** Systems that have a strict, specified *deadline* by which the software *must* respond. 
* **The Stack Requirement:** Providing real-time guarantees requires support from all levels of the software stack: a Real-Time Operating System (RTOS) that allows guaranteed CPU time allocation, library functions that document worst-case execution times, and dynamic memory allocation that is severely restricted.
-  **Real-time vs. High-performance**
	- "Real-time" does **not** mean "high-performance" or "fast." 
	- In fact, real-time systems may have much *lower* throughput because they are forced to prioritize timely, predictable responses above all else. For most server-side data processing, RTOS guarantees are simply not economical or appropriate, so these systems must suffer the pauses and clock instability that come from non-real-time environments.

## Limiting the Impact of Garbage Collection
Since we cannot use real-time systems for standard web services, we have to mitigate GC pauses in other ways. 
1. **Planned Outages:** Treat GC pauses like brief planned outages. The language runtime warns the application that a node needs a GC pause soon. The application stops sending new requests to that node, waits for it to finish processing outstanding requests, and then lets it perform the GC while no requests are in progress. (This trick hides GC pauses from clients).
2. **Rolling Restarts:** Only use the garbage collector for short-lived objects (which are fast to collect). Before the node accumulates enough long-lived objects to require a full "stop-the-world" GC, proactively restart the process entirely. Traffic is routed away from the node during the planned restart.

# Knowledge, Truth, and Lies
Distributed systems differ from single-computer programs because there is no shared memory, only message passing via an unreliable network. These systems may suffer from partial failures, unreliable clocks, and processing pauses. Because problems in the network cannot reliably be distinguished from problems at a node, a node cannot know anything for sure.
## The Truth Is Defined by the Majority
- A node cannot necessarily trust its own judgment of a situation.
	* **The Asymmetric Fault:** A node is able to receive all messages sent to it, but any outgoing messages from that node are dropped or delayed. The other nodes will incorrectly declare it dead, even though it is working perfectly.
	* **The GC Pause:** A node might experience a long stop-the-world garbage collection pause. The other nodes declare it dead, but when the GC finishes, the paused node wakes up and resumes communicating, feeling like hardly any time has passed.
* **The Quorum:** Because a single node's perspective cannot be trusted, many distributed algorithms rely on a quorum (voting among the nodes). Decisions require some minimum number of votes from several nodes in order to reduce the dependence on any one particular node.

## The Leader and the Lock
Frequently, a system requires there to be only one of something (e.g., only one node is allowed to be the leader, or only one transaction can hold a lock to a file).

If a client grabs a lock, goes into a long GC pause, and its lease expires, another client can obtain a lease for the same file. When the paused client wakes up, it incorrectly believes it still has a valid lease and proceeds to write, causing the clients' writes to clash and corrupt the file.
### Fencing Tokens
* **The 3-Player Architecture:** To understand fencing tokens, it helps to recognize that there are three separate entities involved, not just a simple client/server:
    1. **The Client:** The application node that wants to write data.
    2. **The Lock Service (e.g., ZooKeeper):** A highly reliable external service whose only job is managing distributed locks. It issues the lease and generates a strictly increasing fencing token (like a transaction ID).
    3. **The Storage Service:** The actual database or file system where the data is saved. 
* **How it Works:** Every time the Lock Service grants a lease to a Client, it returns the fencing token. When the Client attempts to write to the Storage Service, it must include this token in its request.
* **Server-Side Enforcement:** The Storage Service itself must take an active role in checking tokens by remembering the highest token it has processed and rejecting any subsequent writes that come in with an older token. 
* **The "Downside" of Server-Side Enforcement:** Forcing the Storage Service to check tokens might seem like a bad design because it violates the *separation of concerns*. A storage server should ideally just be a simple, "dumb" bucket that saves files, without having to manage locking logic or track token states. However, you *must* accept this added complexity. Relying on clients to check their own lock status is fundamentally unsafe (because a GC pause can turn a client into a "zombie" that doesn't realize its lock expired). The storage service must actively protect itself from accidentally abusive clients.
## Byzantine Faults
We generally assume that nodes are unreliable but honest: they may be slow or never respond, but if a node does respond, it is telling the "truth" to the best of its knowledge.

Distributed systems problems become much harder if nodes may "lie" (send arbitrary faulty or corrupted responses). This behavior is known as a Byzantine fault, and reaching consensus in this untrusting environment is known as the Byzantine Generals Problem.

* **Where it is used:** A system is Byzantine fault-tolerant if it operates correctly even if nodes malfunction or malicious attackers interfere. This is necessary in aerospace environments (where radiation corrupts computer memory) and in peer-to-peer networks like Bitcoin (where parties attempt to cheat others).
* **Why it is impractical:** In most server-side data systems, the cost of deploying Byzantine fault-tolerant solutions makes them impracticable. 
* **The Bug Problem (Why does using Byzantine fault tolerance against software bugs require four completely different code implementations?):** 
    Can BFT protect you from bugs in your own software? Usually, no. A 4-node BFT system requires a supermajority to function and can tolerate at most *one* malfunctioning node. 
    * **The Deterministic Trap:** If you deploy the exact same software to all four nodes, a bug is deterministic. A specific bad input will cause *all four nodes* to crash or corrupt data at the exact same time, instantly destroying your quorum. 
    * **The N-Version Solution:** To actually survive a software bug using BFT, you cannot run the same code everywhere. You would have to hire four completely separate engineering teams to write four independent implementations of the same software (known as *N-version programming*). This ensures a coding mistake made by one team only takes down 1 node, leaving the other 3 independent nodes to outvote it.
    * **Is this actually done?** For normal companies (building web apps or databases), this is a massive waste of money; it is vastly cheaper and better to just write one codebase, test it, and fix bugs as they happen. This extreme multi-implementation approach is only used in life-or-death systems (like flight control systems on commercial airplanes or rockets) where a single bug causes an immediate crash, meaning you need independent computers to instantly outvote the buggy one in real-time.
* **Weak Forms of Lying (Accidental vs. Malicious):** These are incorrect or invalid messages caused by accidental hardware issues, software bugs, or misconfigurations, rather than deliberate, malicious attacks. Because there is no determined adversary actively trying to break the system, we can guard against these "weak" lies using simple, pragmatic mechanisms instead of complex Byzantine fault tolerance. Examples include using checksums in the application-level protocol to catch corrupted network packets, sanitizing user inputs to prevent large memory allocations, and configuring NTP clients with multiple server addresses to filter out incorrect outliers.

## System Models and Reality
To reason about faults systematically, we formalize the kinds of faults we expect by defining a system model (an abstraction that describes what an algorithm may assume).
### Timing Assumption Models
1. **Synchronous model:** Assumes bounded network delay, bounded process pauses, and bounded clock error. (Not a realistic model of most practical systems).
2. **Partially synchronous model:** Behaves like a synchronous system most of the time, but occasionally shatters timing assumptions with arbitrarily large delays or pauses. (This is a realistic model of many systems).
3. **Asynchronous model:** An algorithm is not allowed to make any timing assumptions whatsoever (it does not even have a clock).

### Node Failure Models
1. **Crash-stop faults:** A node can fail in only one way, namely by crashing and never coming back.
2. **Crash-recovery faults:** Nodes may crash and perhaps start responding again later; they have stable storage that is preserved, while in-memory state is lost. (For modeling real systems, the partially synchronous model with crash-recovery faults is generally the most useful).
3. **Byzantine (arbitrary) faults:** Nodes may do absolutely anything, including tricking other nodes.

## Correctness: Safety and Liveness
An algorithm is correct if it always satisfies its properties in all situations assumed in the system model. These properties are divided into two distinct kinds:

* **Safety Properties (Nothing bad happens):**
    * *Examples:* Uniqueness (no two requests return the same value) and Monotonic sequence (if request *x* completed before request *y* began, the token for *x* must be strictly smaller than the token for *y*).
    * *Characteristics:* If violated, we can point at a particular point in time at which it was broken, and the damage is already done (it cannot be undone). 
    * *The Rule:* Distributed algorithms often require that safety properties *always* hold; even if all nodes crash, the algorithm must nevertheless ensure it does not return a wrong result.
* **Liveness Properties (Something good eventually happens):**
    * *Examples:* Availability (a node eventually receives a response) and eventual consistency.
    * *Characteristics:* It may not hold at some point in time, but there is always hope it may be satisfied in the future.
    * *The Rule:* With liveness properties, we are allowed to make caveats (e.g., a request needs to receive a response only if a majority of nodes have not crashed, and only if the network eventually recovers).

## Theory vs. Implementation (Computer Science vs. Software Engineering)
* **The Role of Theory (Computer Science):** Theoretical, abstract system models are incredibly valuable. They distill the chaotic complexity of real systems down to a manageable set of defined faults, allowing us to mathematically prove that an algorithm is correct under specific assumptions.
* **The Reality of Implementation (Software Engineering):** Real life doesn't always respect the mathematical model. A real-world implementation must include defensive code to handle situations the theoretical model explicitly assumed were "impossible." 
* **The Core Difference:** Even if handling an "impossible" event simply means printing an error message and forcing the process to crash, you still have to write the code for it. This practical necessity of dealing with the messy, unpredictable reality outside the bounds of the mathematical model is arguably the fundamental difference between theoretical computer science and applied software engineering.
## Conclusion: Why Bother with Distributed Systems?
Given all the severe problems discussed in this chapter (unreliable networks, drifting clocks, zombie pauses, and Byzantine faults), it might seem easier to just keep everything on a single, reliable computer. However, that isn't possible for modern applications.

* **The True Value:** Scalability is *not* the only reason for wanting to use a distributed system. **Fault tolerance** (surviving hardware failures without taking the service offline) and **low latency** (placing data geographically close to users) are equally important goals, and neither of those can be achieved with a single, isolated node. We accept the messy reality of distributed systems because the benefits outweigh the pain.
