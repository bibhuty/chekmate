# Consistency and Consensus

Whenever failing an entire service is not an acceptable response to an error, we must find ways of tolerating faults—meaning the service is kept functioning correctly even if some internal component is faulty. Building fault-tolerant systems assumes that all the unreliable realities of distributed networks can and will occur: packets can be lost, reordered, duplicated, or arbitrarily delayed in the network; clocks are approximate at best; and nodes can pause (e.g., due to garbage collection) or crash at any time.

The best approach to building these systems is to find general-purpose abstractions with useful guarantees, implement them once, and let applications rely on those guarantees. Just like the transaction abstraction hides crashes, race conditions, and disk failures from the application, we seek abstractions to hide distributed systems problems. 

One of the most important abstractions is **consensus**: getting all nodes to agree on something. Reaching consensus despite network faults and process failures is a surprisingly tricky problem. However, it is essential; for example, if two nodes both believe they are the leader (a "split brain" scenario), it often leads to data loss.

# Consistency Guarantees
Because write requests arrive at different replicas at different times, looking at two database nodes at the exact same moment will likely reveal different data. 
* **Eventual Consistency:** Most replicated databases provide this weak guarantee, meaning if you stop writing to the database and wait for some unspecified length of time, eventually all read requests will return the same value. 
* **Convergence:** A better name for eventual consistency may be *convergence*, as we expect all replicas to eventually converge to the same value.

## The Cost of Stronger Guarantees
Systems with stronger guarantees may have worse performance or be less fault-tolerant than systems with weaker guarantees. 
* **Worse Performance:** To provide strong guarantees (like ensuring everyone sees the absolute latest data), nodes must constantly communicate and wait for each other to coordinate a single "truth" before responding to a user's request. This mandatory network coordination adds latency to every operation.
* **Less Fault-Tolerant:** If a network link breaks between datacenters, nodes cannot coordinate. A system with a weak guarantee (eventual consistency) will simply give the user whatever stale data it currently has, remaining available. A system with a strong guarantee will refuse to process the user's request entirely because it cannot safely coordinate the truth. It sacrifices availability to maintain consistency.

# Linearizability
- This is the idea of making a system appear as if there were only one copy of the data, and all operations on it are atomic. It is also known as atomic consistency, strong consistency, immediate consistency, or external consistency.
- If a database has this guarantee, the application does not need to worry about multiple replicas. Fundamentally, linearizability is a **recency guarantee**. As soon as one client successfully completes a write, all clients reading from the database must be able to see the value just written.

## What Makes a System Linearizable?
- In distributed systems literature, a single object (like one key in a key-value store, one row in a relational database, or one document in a document database) is called a **register**. 
- If a read request is concurrent with a write request (they overlap in time), the read may return either the old or the new value. A register in which reads may return either the old or the new value if they are concurrent with a write is known as a *regular register*. 
- However, a regular register is not enough for linearizability. To be linearizable, the system must add another constraint: 
	* After any one read has returned the new value, all following reads (on the same or other clients) must also return the new value. 
	* We imagine that there must be some specific point in time (between the start and end of the write operation) at which the value of the register atomically flips. 
	* A system's behavior can be tested for linearizability by recording the timings of all requests and responses and checking whether they can be arranged into a valid sequential order.
# Linearizability Versus Serializability
These are easily confused because both imply things can be arranged in a sequential order, but they are quite different guarantees.

* **Serializability:** This is an isolation property of *transactions*. It guarantees that transactions behave the same as if they had executed in some serial order. It can cover operations across multiple objects, rows, or documents. It is okay for that serial order to be different from the actual real-world order in which they were run.
* **Linearizability:** This is a recency guarantee on reads and writes of an *individual object* (a register). It does not group operations into transactions, so it does not naturally prevent problems like write skew.
* **Strict Serializability:** A database may provide both guarantees, a combination known as strict serializability or strong one-copy serializability (examples include two-phase locking or actual serial execution).
* **Snapshot Isolation:** Serializable snapshot isolation (SSI) is explicitly *not* linearizable. By design, it makes reads from a consistent snapshot to avoid lock contention, meaning it purposely does not include writes that are more recent than the snapshot.

# Relying on Linearizability
While having a linearizable view of sports scores might just be for convenience, there are several areas where linearizability is an important requirement for making a system work correctly.
### Locking and Leader Election
* A system using single-leader replication needs to ensure there is indeed only one leader to avoid a split brain scenario.
* No matter how a lock is implemented for leader election, it must be linearizable.
* All nodes must agree which node owns the lock; otherwise, the lock is useless.
### Constraints and Uniqueness Guarantees
* Uniqueness constraints are common in databases, requiring that there is a single up-to-date value that all nodes agree on.
* Examples of this requirement include ensuring a bank account balance never goes negative, not selling more items than are in stock in a warehouse, or preventing two people from concurrently booking the same flight seat.
### Cross-Channel Timing Dependencies
* A system often uses multiple communication channels operating at different speeds (like a fast message queue alongside a slower database). If an application relies on both simultaneously, it opens the door for hidden race conditions.
* **The Example (The Image Resizer):** 
    1. A user uploads a photo. The web server saves this new photo to a file storage service.
    2. Immediately after the save confirms, the web server sends a quick instruction via a message queue to a background "image resizer" worker: *"Hey, go generate a thumbnail for this new photo."*
    3. The image resizer instantly receives the message from the queue and asks the file storage service for the photo.
* **The Nonlinearizable Failure:** If the file storage service is *not* linearizable (e.g., it suffers from internal replication lag), the fast message queue will outpace the storage replication. The resizer will ask a lagging storage replica for the photo, see an old version of the image (or nothing at all), and permanently corrupt the resizing process. 
* **The Linearizable Solution:** If the file storage *is* linearizable, it provides a strict recency guarantee. The resizer is mathematically guaranteed to see the new photo because the web server's write operation fully completed before the resizer's read operation began.

# Implementing Linearizable Systems
Different replication methods offer different potentials for linearizability:
* **Single-leader replication (potentially linearizable):** If you make reads from the leader, or from synchronously updated followers, they have the potential to be linearizable. Partitioning (sharding) a single-leader database does not affect linearizability since it is only a single-object guarantee. 
    * *The Catch:* It **is** linearizable when reading from the true leader or a synchronous follower, but it **is not** linearizable if the system uses asynchronous replication (where failovers lose writes), snapshot isolation (by design), or if a disconnected, "delusional" leader continues to serve reads during a split-brain scenario.
* **Consensus algorithms (linearizable):** These algorithms contain measures to prevent split brain and stale replicas, allowing them to implement linearizable storage safely.
* **Multi-leader replication (not linearizable):** These systems concurrently process writes on multiple nodes and asynchronously replicate them, which can produce conflicting writes.
* **Leaderless replication (probably not linearizable):** People sometimes claim you can obtain "strong consistency" by requiring quorum reads and writes (w + r > n), but depending on the configuration of the quorums and the definition of strong consistency, this is not quite true.

## Linearizability and Quorums
Intuitively, it seems as though strict quorum reads and writes ($w + r > n$) in a Dynamo-style model should be linearizable. However, due to variable network delays, race conditions are still possible, making them **nonlinearizable**:
* **The Race Condition:** Imagine a writer is updating a value from 0 to 1 across three replicas. Due to variable network delays, the write reaches some replicas faster than others.
* **Reader A (Sees New Value):** Concurrently, Reader A queries a quorum of two nodes, hits a node that already received the write, and successfully returns the new value (1). Reader A's read request completes.
* **Reader B (Sees Old Value):** *After* Reader A's request finishes, Reader B initiates a read against a different quorum of two nodes that have not yet received the delayed write. Reader B returns the old value (0).
* **The Violation:** This is a direct violation of linearizability's recency guarantee. Reader B's request began strictly after Reader A's request completed, yet Reader B received an older value than Reader A.
* **The Cost of Fixing It:** It is possible to make Dynamo-style quorums linearizable, but only at the cost of reduced performance. A reader must perform synchronous *read repair* before returning results to the application, and a writer must read the latest state of a quorum before sending writes. Databases like Riak and Cassandra typically avoid this because of the severe performance penalty.

### `NOTE`: How Quorum Reads Actually Work (Recency vs. Majority)
It is a common misconception that a quorum acts like a democracy (e.g., if 3 out of 5 queried nodes return the value "A", then "A" wins the majority vote). This is **not** how it works.
* **Version Numbers, Not Votes:** When a database saves data, it attaches a strictly increasing version number (or timestamp). During a quorum read, the system asks the nodes for both their value *and* its version number.
* **Finding the Newest Data:** If a read quorum queries three nodes and gets two responses of "A (Version 1)" and one response of "B (Version 2)", the system immediately discards the majority and returns "B" because it has the highest version number.
* **The Math ($w + r > n$):** The strict quorum formula is simply a mathematical guarantee (the pigeonhole principle). It ensures that your read quorum will always overlap with at least one node from the most recent write quorum, guaranteeing that the system will encounter that highest version number.

# The Cost of Linearizability

## The CAP Theorem
The trade-off regarding network interruptions and linearizability is as follows:
* If your application requires linearizability, and some replicas are disconnected due to a network problem, those replicas cannot process requests and become unavailable (they must wait for the network to fix or return an error).
* If your application does not require linearizability, it can be written so replicas process requests independently. In this case, the application can remain available in the face of a network problem, but its behavior is not linearizable.

## The Unhelpful CAP Theorem
* CAP is sometimes presented as Consistency, Availability, Partition tolerance: pick 2 out of 3.
* Putting it this way is misleading because network partitions are a kind of fault; they are not something about which you have a choice, as they will happen whether you like it or not.
* * **The CAP Trade-off in Reality:** 
    * **When the network is healthy:** A system *can* provide both consistency (linearizability) and total availability. Physical replication lag still happens, but because the network is fast, nodes can synchronously coordinate in milliseconds to hide the lag and return a successful, consistent response.
    * **When a network fault occurs (Partition):** Nodes can no longer communicate to resolve replication lag. The system is forced to choose: either wait forever/return an error (sacrificing total availability) or return stale, lagging data (sacrificing linearizability).
* A better way of phrasing CAP would be *either Consistent or Available when Partitioned*.

## The Unhelpful CAP Theorem (Why it causes confusion)
All in all, the CAP theorem is best avoided in practical system design because its formalization creates significant misunderstanding:

* **"Pick 2 of 3" is Misleading:** CAP is often presented as choosing two out of Consistency, Availability, and Partition tolerance. However, network partitions (communication faults between nodes) are a reality of physics, not an optional design choice. You cannot choose *not* to have network faults; they will happen whether you like it or not.
* **The Definition of "Availability":** The formal mathematical proof of CAP uses an idiosyncratic definition of "availability" that completely contradicts what software engineers mean when building highly available systems:
    * *CAP's Theoretical Definition:* A non-failing node must eventually return a valid, non-error response. It places absolutely no bounds on latency. If a node takes 10 minutes to coordinate and respond, it is mathematically considered "available" under CAP.
    * *Engineers' Practical Definition:* High availability means a system responds quickly and reliably. To a real-world user, a system that takes 10 minutes to load a page is completely broken and unavailable. 
* **An Extremely Narrow Scope:** The formal theorem only considers *one* specific consistency model (linearizability) and *one* specific kind of fault (network partitions, meaning nodes are alive but disconnected). It says absolutely nothing about other practical consistency models (like eventual or causal consistency) or other everyday faults (like network delays, paused processes, or dead nodes).
    * **Questions about other faults:** 
	    * What trade-offs must my system make if a node physically crashes and dies, rather than just being disconnected?
	    * How should the system behave if the network isn't partitioned, but is just experiencing severe latency spikes and delayed packets?
	    * What happens to consistency if a node is alive and connected, but frozen due to a massive garbage collection pause?
    * **Questions about other consistency models:** 
	    * If my application doesn't need strict linearizability and can settle for *causal consistency*, how does that change my behavior during a network partition?
	    * If I use *eventual consistency*, what are the mathematical bounds on how stale my data is actually allowed to get while the nodes resolve their differences?
* **The Verdict:** Due to its contradictory definitions, misleading framing, and failure to account for the reality of multifaceted system faults and alternative consistency models, the CAP theorem is mostly of historical interest. It has very little practical value for actually designing distributed systems today.
## The Unrealistic Assumptions of the CAP Theorem
The formal CAP theorem is a mathematical proof. To make the math work, its creators had to define their variables so rigidly that they stripped away the messy, practical realities of software engineering. The theorem's assumptions are considered far too strict for day-to-day system design:

* **The "C" Assumption (Absolute Recency):** CAP assumes that "Consistency" *only* counts if it is strict linearizability (an illusion of a single, instantaneous copy of the data). In the real world, most applications (like social feeds, messaging apps, or shopping carts) function perfectly well with Causal Consistency or Eventual Consistency. By refusing to acknowledge these other models, CAP forces a false dilemma.
* **The "A" Assumption (Infinite Patience):** CAP assumes a node is "Available" as long as it doesn't crash and *eventually* returns a non-error response. It makes zero assumptions about latency. Under CAP's strict mathematical model, a database that freezes for two hours before returning a successful read is technically considered "Available." To a real-world engineer or user, a two-hour latency is a complete outage.
* **The "P" Assumption (Only One Type of Failure):** CAP assumes the *only* thing that goes wrong is a clean network partition (a severed cable or dropped connection between perfectly healthy nodes). It completely ignores the vast majority of everyday distributed systems failures, such as crashed nodes, full disks, massive clock drift, or nodes frozen by garbage collection pauses.
## Linearizability and Performance
* Many distributed databases choose not to provide linearizable guarantees primarily to increase performance, not so much for fault tolerance.
* Linearizability is slow all the time, not only during a network fault.
* A faster algorithm for linearizability does not exist, but weaker consistency models can be much faster, making this trade-off important for latency-sensitive systems.

# Ordering Guarantees
* A linearizable register behaves as if there is only a single copy of the data, and that every operation appears to take effect atomically at one point in time. 
* Ordering has been a recurring theme, which suggests that it might be an important fundamental idea. 
* We have seen ordering arise in several contexts previously:
    * In single-leader replication, the main purpose of the leader is to determine the order of writes in the replication log.
    * Serializability is about ensuring that transactions behave as if they were executed in some sequential order.
    * The use of timestamps and clocks in distributed systems is another attempt to introduce order.
## Ordering and Causality
* There are several reasons why ordering keeps coming up, and one of the reasons is that it helps preserve causality. 
* Causality imposes an ordering on events where the cause must precede the effect, such as the causal dependency between the question and the answer.
* Other examples of causality include:
    * Causality here means that a row must first be created before it can be updated.
    * If you have two operations A and B, there are three possibilities: either A happened before B, or B happened before A, or A and B are concurrent. This happened before relationship is another expression of causality.
    * In snapshot isolation, a snapshot that is consistent with causality means that if the snapshot contains an answer, it must also contain the question being answered.
    * Serializable snapshot isolation detects write skew by tracking the causal dependencies between transactions.
* If a system obeys the ordering imposed by causality, we say that it is causally consistent. e.g. snapshot isolation
## The Causal Order is Not a Total Order
* A total order allows any two elements to be compared, so if you have two elements, you can always say which one is greater and which one is smaller.
* Mathematical sets and causality are partially ordered, meaning in some cases items are incomparable.
* The difference between a total order and a partial order is reflected in different database consistency models:
    * **Linearizability:** In a linearizable system, we have a total order of operations: if the system behaves as if there is only a single copy of the data, and every operation is atomic, this means that for any two operations we can always say which one happened first. 
	    * Therefore, there are no concurrent operations in a linearizable datastore; there must be a single timeline along which all operations are totally ordered.
    * **Causality:** Events are ordered if they are causally related, but they are incomparable if they are concurrent. This means that causality defines a partial order, not a total order: some operations are ordered with respect to each other, but some are incomparable. 
	    * Concurrency would mean that the timeline branches and merges again.
## Linearizability is Stronger than Causal Consistency
* The relationship between causal order and linearizability is that linearizability implies causality.
* A system can be causally consistent without incurring the performance hit of making it linearizable (in particular, the CAP theorem does not apply). 
* Causal consistency is the strongest possible consistency model that does not slow down due to network delays, and remains available in the face of network failures.

# Sequence Number Ordering
* Tracking all causal dependencies can become impracticable, so instead, we can use sequence numbers or timestamps to order events. 
* Rather than a physical clock, a timestamp can come from a logical clock, which is an algorithm to generate a sequence of numbers to identify operations, typically using counters that are incremented for every operation.
## Noncausal Sequence Number Generators
* If there is not a single leader (perhaps because you are using a multi-leader or leaderless database, or because the database is partitioned), it is less clear how to generate sequence numbers for operations.
* Various methods are used in practice:
    * Each node can generate its own independent set of sequence numbers.
    * You can attach a timestamp from a time-of-day clock (physical clock) to each operation, a method utilized in last write wins conflict resolution.
    * You can preallocate blocks of sequence numbers.
* While scalable, the sequence numbers they generate are not consistent with causality.
* The causality problems occur because these sequence number generators do not correctly capture the ordering of operations across different nodes:
    * Each node may process a different number of operations per second... If you have an odd-numbered operation and an even-numbered operation, you cannot accurately tell which one causally happened first.
    * Timestamps from physical clocks are subject to clock skew, which can make them inconsistent with causality (e.g., assigning an operation that happened causally later a lower timestamp).
    * In the case of the block allocator, one operation may be given a sequence number in the range from 1,001 to 2,000, and a causally later operation may be given a number in the range from 1 to 1,000.
## Lamport Timestamps
* There is actually a simple method for generating sequence numbers that is consistent with causality. It is called a Lamport timestamp.
* A Lamport timestamp bears no relationship to a physical time-of-day clock, but it provides total ordering: if you have two timestamps, the one with a greater counter value is the greater timestamp; if the counter values are the same, the one with the greater node ID is the greater timestamp.
* While version vectors can distinguish whether two operations are concurrent or whether one is causally dependent on the other, whereas Lamport timestamps always enforce a total ordering. 
* Consequently, from the total ordering of Lamport timestamps, you cannot tell whether two operations are concurrent or whether they are causally dependent.
* The advantage of Lamport timestamps over version vectors is that they are more compact.
### NOTE: Lamport Timestamps vs. Version Vectors (The Trade-off)
* **Version Vectors (The Full Picture):** They use a bulky array to track the counter of *every single node* (e.g., `[Node A: 2, Node B: 1]`). 
    * *Example:* If Node A and Node B both do an update without seeing each other's work, their arrays won't match up. The system mathematically proves they are **concurrent** and flags a conflict.
* **Lamport Timestamps (The Forced Single Line):** They compress everything into a single maximum integer plus a tie-breaker ID (e.g., `Counter: 5, Node A`). 
    * *Example:* If Node A and Node B concurrently generate `Counter: 5`, Lamport doesn't care that they happened at the exact same time. It just looks at the tie-breaker and arbitrarily decides that Node B happened "after" Node A. It forces a clean, total order, but permanently destroys the ability to detect that the events were actually concurrent.

### Timestamp Ordering is Not Sufficient
* The problem here is that the total order of operations only emerges after you have collected all of the operations. 
* If another node has generated some operations, but you don't yet know what they are, you cannot construct the final ordering of operations: the unknown operations from the other node may need to be inserted at various positions in the total order.
* To conclude: in order to implement something like a uniqueness constraint for usernames, it's not sufficient to have a total ordering of operations—you also need to know ***when that order is finalized***.

## Total Order Broadcast
* The concept of identifying exactly when a sequence of operations is finalized is addressed by total order broadcast.
* It is sometimes referred to as atomic broadcast or total order broadcast/multicast, though "atomic" can cause confusion with ACID transactions. 
* At its core, total order broadcast is a protocol for nodes to exchange messages while strictly adhering to two safety properties:
    1. **Reliable delivery:** Messages cannot be lost; delivering a message to a single node guarantees delivery to all nodes.
    2. **Totally ordered delivery:** Every single node receives the messages in the exact same sequence.

### Using Total Order Broadcast
* Systems that process these identically ordered messages will inherently stay consistent with one another, a concept known as ***state machine replication***.
* A critical feature of this protocol is that the sequence is permanently locked in at the ***moment of delivery***. A node cannot go back and insert a delayed message earlier in the timeline, which makes this protocol strictly stronger than timestamp ordering.
* This mechanism essentially acts as a log (like a transaction or replication log).
* It is also highly effective for creating a lock service that issues monotonically increasing fencing tokens. 

### Total Order Broadcast vs. Linearizability
* While total order broadcast guarantees the order of messages, it is asynchronous regarding *when* they are delivered, so there can be replication lag. Linearizability, on the other hand, is a strict recency guarantee ensuring reads see the absolute latest written value, i.e. no replication lag.
#### Asynchronous Delivery and Node Lag
* **No Errors on Lag:** Total order broadcast guarantees reliable delivery, but the delivery itself is asynchronous. If a recipient node lags behind due to network delays, it does not error out or require the sender to manually retry. The protocol ensures the lagging node will eventually receive the delayed messages in the correct sequence.
* **The Cost of Lag (Stale Reads):** This physical lag is exactly why total order broadcast is *not* linearizable on its own. If a client queries a lagging node, that node will successfully process the read request, but it will return **stale data** because it has not yet received the most recent broadcast messages.

#### Implementing Linearizable Writes using Total Order Broadcast
You can build a linearizable compare-and-set operation (like claiming a unique username) using total order broadcast as an append-only log:
1. Tentatively append your desired username claim to the broadcast log.
2. Read the log and wait until you see your own appended message delivered back to you.
3. Check if any other node's claim for that username appears before yours in the log. If your message is first, you successfully commit. If someone else's message came first, you abort.

#### Making Reads Linearizable
The procedure above ensures linearizable writes, but reads might still be stale (providing only *sequential/timeline consistency*). To force linearizable reads, you can:
* Send a read request as a broadcast message, wait for it to be delivered, and read the state at that exact position in the log.
* Fetch the position of the absolute latest log message, wait for your local node to catch up to that exact position, and then perform the read.
* Route your read to a replica that is guaranteed to be synchronously updated.

#### Implementing Total Order Broadcast using Linearizability
The relationship works in reverse, too. If you have a linearizable integer (like an atomic increment-and-get register), you can build total order broadcast:
* For every message, increment the linearizable integer and attach that number to the message. 
* Send the message to all nodes. 
* Unlike Lamport timestamps, this creates a sequence with zero gaps. If a node receives message 4 and then message 6, it mathematically knows it must wait for message 5 before proceeding.

#### The Mathematical Equivalence of Consensus, TOB, and Linearizability
* **The Core Concept:** It can be mathematically proven that linearizable registers, total order broadcast (TOB), and consensus are equivalent problems. If a system can solve one of these problems, that solution can be transformed to solve the others. 
* **Consensus $\rightarrow$ Total Order Broadcast:** Consensus is simply getting nodes to agree on a single decision. By repeatedly using a consensus algorithm to agree on what the *next* message in a sequence should be, you successfully build a Total Order Broadcast protocol.
* **Total Order Broadcast $\rightarrow$ Linearizable Registers:** TOB guarantees a strictly ordered, append-only log. By having nodes read and write to this guaranteed log, you can safely implement atomic operations (like a compare-and-set register used for claiming unique usernames).

# Distributed Transactions and Consensus

## The Impossibility of Consensus (FLP Result)
* The FLP result is a famous mathematical proof stating that in a purely asynchronous system, no algorithm can guarantee consensus if there is even a risk of a single node crashing. , make a decision, and move forward, making consensus solvable in the real world.
#### Overcoming the FLP Impossibility (Failure Detectors)
* **The Trap of the Asynchronous Model:** The FLP impossibility proof relies on a strict "asynchronous system model" that has no clocks and no limits on network delays. In this theoretical model, it is mathematically impossible to distinguish between a node that has permanently crashed and a node that is just severely delayed. Because the algorithm can never be sure, it is forced to wait forever, making consensus impossible.
* **The Practical Solution:** To solve consensus in the real world, systems break the strict rules of the asynchronous model by introducing mechanisms to identify suspected crashes.
* **How it Works:** By using **timeouts** or **other methods** (e.g., checking if a network socket dropped, relying on heartbeat messages, or having the host operating system report a process failure), the system can flag a silent node as "suspected dead." Even if this suspicion is occasionally wrong (flagging a slow node as dead), it allows the algorithm to stop waiting, safely bypass the stalled node, and move the system forward.
## Atomic Commit vs. Consensus
Both atomic commit and general consensus are fundamentally distributed voting systems. They solve the exact same core problem: getting a group of independent nodes to agree on a single, permanent outcome. However, while the mechanism of gathering votes is the same, their rules and applications differ significantly.

* **Atomic Commit Win Condition (Unanimity):** Every single participant must vote "Yes" to commit the transaction. If even one node votes "No" (or crashes), the final agreed-upon decision must be to abort the entire system.
* **Consensus Win Condition (Majority):** Requires only a quorum. As long as a majority of nodes agree on a proposed value, the decision is safely locked in, even if a minority of nodes vote differently or are currently dead.
* **Reducibility (Building one with the other):** Because they share this underlying voting DNA, you can use one protocol to implement the other. For example, you can run a fault-tolerant consensus algorithm (where a majority rules) to safely agree upon and persistently record the final outcome of a fragile atomic commit transaction (where strict unanimity was required among the participants).

# Distributed Transactions and Two-Phase Commit (2PC)

The purpose of transaction atomicity is to prevent failed operations from littering the database with half-finished results. 
## Single-Node vs. Distributed Atomic Commit
* **Single-Node Commit:** On a single node, atomicity relies heavily on the *order* of durable disk writes. The database writes the data to the log, and the transaction is officially committed the exact moment the final "commit record" finishes writing to the disk. 
* **The Distributed Problem:** When multiple nodes are involved, you cannot simply send an independent commit request to each node. If you do, atomicity is violated because some nodes might succeed while others fail (due to constraint violations, network timeouts, or crashes).
* **The Rule of Irrevocability:** A transaction commit must be irrevocable. A node must only commit once it is absolutely certain all other participating nodes will also commit.
* **Compensating Transactions:** While you cannot "un-commit" a transaction, you can write an application-level *compensating transaction* to safely undo the effects of a previously committed one.

## Introduction to Two-Phase Commit (2PC)
Two-phase commit is the classic algorithm for ensuring all nodes commit or all nodes abort in a distributed system. 
* **Do not confuse 2PC with 2PL:** 2PC provides *atomic commit*, whereas 2PL (Two-Phase Locking) provides *serializable isolation*.
* **The Coordinator:** 2PC introduces a new component called the *coordinator* (or transaction manager), which tracks the workflow. 

### Phase 1: The Prepare Phase (A System of Promises)
When the application is ready to commit, the coordinator sends a *prepare* request to all participant nodes. 
* **Making the Promise:** When a participant receives a prepare request, it must ensure it can definitely commit under *any* circumstances. It writes all data to disk (crashing or running out of space is no longer an acceptable excuse) and checks for conflicts. 
* **Under the Hood (MVCC & Locks):** The participant actually executes the writes down to disk during this phase—creating new row versions (tagged with a transaction ID) and taking row-level locks. It holds these locks and keeps the new versions hidden until the final decision.
* **The Point of No Return:** By replying "yes," the node makes a strict promise to commit later. It formally surrenders its right to abort the transaction unilaterally (though the coordinator can still choose to abort if another node votes "no").

### Phase 2: The Commit Phase
* **The Commit Point:** When the coordinator receives "yes" votes from every participant, it makes a definitive decision to commit. It must write this decision to its own transaction log on disk. This disk write is the official *commit point*.
* **Flipping the Switch:** Because data is already written in Phase 1, Phase 2 is lightweight: the participant simply updates the transaction's status to "committed" in its status table (making the new versions visible) and releases its locks.
* **Infinite Retries:** Once the coordinator's decision is on disk, it sends the commit request to all participants. If the network fails or a node crashes at this stage, the coordinator must retry *forever* until it succeeds.

## Coordinator Failure and "In-Doubt" Transactions

If a participant votes "yes" in Phase 1, it is locked in. If the coordinator crashes or the network fails before Phase 2 arrives, the participant can do nothing but wait. A transaction in this state is called **in doubt** or **uncertain**.
### The Coordinator as a Single Point of Failure
* **The Ultimate Bottleneck:** Despite being a distributed protocol designed for multiple machines, the final deciding moment of 2PC comes down to a regular, single-node atomic commit on the coordinator's local disk drive. 
* **System-Wide Halt:** Because of this design, the coordinator acts as a critical single point of failure (SPOF). If the coordinator is not replicated (which many aren't by default) and crashes, the fate of the entire distributed transaction rests on that single machine recovering. 
* **The "In-Doubt" Paralysis:** Any participant nodes that voted "yes" right before the crash are left stranded. They must sit indefinitely in an "in-doubt" state, forced to hold onto their locks and block other operations until the coordinator comes back online to tell them what its final decision was.

### The Danger of Holding Locks While In Doubt
Why does an in-doubt transaction matter? Because of database locking.
* To prevent dirty writes or provide serializable isolation, databases take exclusive or shared locks on modified/read rows. 
* **The database cannot release those locks until the transaction commits or aborts.**
* If the coordinator crashes and takes 20 minutes to recover, those locks are held for 20 minutes, completely blocking other transactions from modifying (and potentially reading) those rows. 

### Recovering from Coordinator Failure
If the coordinator's log is permanently lost or corrupted, orphaned in-doubt transactions will sit in the database forever, holding locks. 
* **Manual Intervention:** As you noted with your "BEST" margin comment, the highly stressful reality is that an administrator must manually intervene, inspect the nodes, and force a commit or rollback to resolve the blockage.
* **Heuristic Decisions:** Many implementations offer an emergency escape hatch called a *heuristic decision*, which allows a participant to unilaterally break its promise and decide to abort or commit. This is only for catastrophic outages, as it likely breaks atomicity.

## Three-Phase Commit (3PC) & Failure Detectors
2PC is called a *blocking* atomic commit protocol because it can get stuck waiting for the coordinator to recover. 
* **Three-Phase Commit (3PC)** was proposed as a non-blocking alternative so that the system doesn't get stuck if a node fails. 
* **The Flawed Assumption of 3PC:** The 3PC algorithm theoretically works, but it strictly assumes a network with **bounded delays** and nodes with **bounded response times**. 
    * **The "Weird" Reality:** This essentially means the algorithm relies on the impossible assumption that the coordinator (and every other node) will *always* process a request and respond within a strictly guaranteed time limit.
* **Why 3PC fails in practice:** In real-world systems, network delays are unbounded and processes experience unpredictable pauses (like garbage collection). In such environments, non-blocking atomic commit requires a **perfect failure detector**—a reliable mechanism for distinguishing between a node that has genuinely crashed and one that is just temporarily slow. 
* Because a standard timeout might trigger due to a simple network spike (not an actual crash), perfect failure detection is impossible in practice. If 3PC acts on a false timeout, it cannot guarantee atomicity. For this reason, 2PC remains the standard despite its blocking problems.
## Distributed Transactions in Practice
Distributed transactions carry a mixed reputation, often criticized for operational complexity and killing performance. 

### The Performance Penalty of 2PC
* **The 10x Slowdown:** Distributed transactions carry a heavy performance penalty. For example, they can be over 10 times slower than standard single-node transactions.
* **Root Cause 1: Disk Forcing (fsync):** To guarantee crash recovery, 2PC relies on strict, synchronous disk writes. Before replying to a phase, both the coordinator and every single participant must force (`fsync`) data from volatile RAM directly into their Write-Ahead Log (stable storage). 
* **Root Cause 2: Network Overhead:** The protocol inherently requires multiple network round-trips (the Prepare request, the Yes/No vote, the Commit request, and the final acknowledgement) across every node, severely compounding the latency of the disk writes.

### Two Types of Distributed Transactions
1. **Database-Internal:** All nodes participating are running the exact same database software. These work quite well because they can apply technology-specific optimizations.
2. **Heterogeneous:** The participants are different technologies (e.g., mixing a PostgreSQL database with a message broker). 

### XA Transactions
**X/Open XA** is the standard API for implementing two-phase commit across heterogeneous technologies. 
* It is a C API (not a network protocol) that application network drivers/libraries use to interface with the transaction coordinator. 
* It allows powerful integrations, like **exactly-once message processing** (consuming a message from a queue and writing to a database in one atomic sweep, discarding side effects if the transaction aborts).
    * **Practical Example (Food Delivery Pipeline):** An app must process a "Masala Dosa" order by removing the message from a broker (ActiveMQ) and inserting it into a database (PostgreSQL).
        * **Phase 1 (Prepare):** The transaction coordinator uses XA to ask both systems to prepare. PostgreSQL writes the order to disk and locks the row; ActiveMQ marks the message as "pending" on disk. Both vote "Yes."
        * **Phase 2 (Commit):** The coordinator logs the commit decision. PostgreSQL makes the row visible, and ActiveMQ permanently deletes the message. 
        * **Failure Safety:** If a database constraint fails in Phase 1, PostgreSQL votes "No." The coordinator aborts everything: PostgreSQL discards the row, and ActiveMQ safely returns the order message to the queue to prevent it from being lost.

## Limitations of Heterogeneous Distributed Transactions

* **Lowest Common Denominator:** Because XA must be compatible with a vast array of different data systems, it is forced to operate at the weakest common guarantee. For example, it cannot detect deadlocks across different systems or work with advanced features like Serializable Snapshot Isolation (SSI).
* **Stateful Deployments:** Server-side applications are traditionally stateless, allowing them to be easily spun up or torn down. However, embedding an XA coordinator into the application server changes this. The coordinator's local disk logs become a critical part of the durable system state, significantly complicating deployments.
* **The Coordinator is a Database:** The transaction coordinator stores transaction outcomes, meaning it is fundamentally a kind of database itself. It must be approached with the exact same operational care as any other critical database.
* **Single Point of Failure & Poor HA:** If the coordinator is not replicated and runs on a single machine, it becomes a single point of failure for the entire system (causing other servers to block on locks if it crashes). Surprisingly, many XA coordinator implementations are not highly available by default and offer only rudimentary replication support.
* **Amplifying Failures:** In a distributed transaction, if *any* single part of the system is broken, the entire transaction fails. Instead of providing fault tolerance, distributed transactions inherently amplify failures.

# Fault-Tolerant Consensus Fundamentals
- The consensus problem is formally defined as follows: one or more nodes may propose values, and the consensus algorithm must decide on one of those proposed values.
- To be considered a true consensus algorithm, it must satisfy four strict properties:
	*   **Uniform agreement:** No two nodes are allowed to decide differently.
	*   **Integrity:** No node is allowed to decide twice.
	*   **Validity:** If a node decides on a value `v`, then `v` must have been proposed by some node (it cannot just invent a default "null" decision out of thin air).
	*   **Termination:** Every node that does not crash must *eventually* decide on some value. It assumes that when a node "crashes", it suddenly disappears and never comes back
- The first three (Agreement, Integrity, Validity) are **safety properties**—they ensure nothing bad happens. Termination is a **liveness property**—it ensures the system actually makes progress and doesn't sit around forever.
- How does 2PC not meet the requirements for termination?
	*   The consensus system model mathematically assumes that when a node crashes, it is destroyed (e.g., buried in a landslide) and will *never come back*. 
	*   In Two-Phase Commit (2PC), if the coordinator crashes, the in-doubt participants are forced to wait for it to recover. 
	*   Because the model assumes the coordinator is never coming back, those in-doubt nodes will wait for infinity. They will never "eventually decide a value." Thus, 2PC completely fails the Termination property.
## Fault Tolerance Thresholds
*   **The Majority Rule:** The termination property is strictly subject to the assumption that *fewer than half* of the nodes are crashed. You need a quorum (a strict majority) to make progress. For example, a 3-node system tolerates 1 failure; a 5-node system tolerates 2 failures.
*   **Safety Survives Outages:** Even if a massive network partition breaks your majority (causing the system to halt and fail Termination), a well-designed consensus algorithm will still uphold the safety properties (Agreement, Integrity, Validity). A large outage can stop the system, but it cannot corrupt it.
*   **Byzantine Faults:** Most standard algorithms assume no Byzantine faults (nodes lying or sending contradictory messages). It is possible to survive Byzantine faults, but only if fewer than one-third of the nodes are malicious/broken.
### Why Network Partitions Don't Break Safety
Imagine a 5-node cluster split by a network partition into two isolated sides: **Partition A (2 stale nodes)** and **Partition B (3 up-to-date nodes)**.
* **The Write Attempt:** If a client sends a write request to Partition A, the node receives it and asks its peers for votes to commit the value.
* **The Quorum Failure:** Consensus requires a strict majority (a quorum) to make any decision. In a 5-node system, a quorum is **3**. Partition A only has 2 nodes, meaning it mathematically cannot achieve a quorum.
* **Safety over Liveness:** Because Partition A cannot get 3 votes, the write request simply fails or times out. By halting and refusing to process the request (sacrificing the *Termination/Liveness* property), the system prevents a split-brain reality, perfectly preserving its *Safety* properties.
### The Safety of Overlapping Quorums
What happens if a request is routed to a partition containing stale nodes?
* **If the stale partition is a minority:** The nodes cannot reach a quorum (majority). They are unable to elect a leader, and all read/write requests will fail or time out, preserving safety.
* **If the stale partition is a majority:** It is mathematically impossible for the *entire* majority to be stale. Because any two majorities in a cluster must overlap by at least one node, the new majority partition is guaranteed to contain at least one node with the most up-to-date committed data.
    * **The Election Check:** Consensus algorithms (like Raft or Paxos) require that the winner of a leader election has the most up-to-date log. The node with the fresh data will win the election and force the stale nodes to update their data before serving any new client requests.
# Consensus & Total Order Broadcast

Consensus (deciding a single value once) and Total Order Broadcast (delivering a sequence of messages exactly once, in the same order, to all nodes) are fundamentally equivalent. Total Order Broadcast is just repeated rounds of consensus. 

When mapped to consensus properties:
*   **Agreement** means all nodes deliver the same messages in the same order.
*   **Integrity** means messages are not duplicated.
*   **Validity** means messages are not corrupted/fabricated.
*   **Termination** means messages are not lost.

Real-world ***algorithms*** like Raft, Zab, and Multi-Paxos skip doing "one-value-at-a-time" consensus because implementing Total Order Broadcast directly is far more efficient.

### Is Consensus a Single-Leader Theory?
While consensus and single-leader replication often look identical in practice, there is a strict difference between the academic theory and the real-world implementation:
*   **The Academic Theory:** Theoretically, consensus does not require a single leader. A cluster could operate democratically, executing a free-for-all vote for every single message or write request that enters the system.
*   **The Practical Reality:** Executing a massive, cluster-wide vote for every individual database write is incredibly slow. To bypass this performance bottleneck, algorithms like Raft and Multi-Paxos optimize the process by electing a single leader to handle all writes. 
*   **The Conundrum:** This optimization turns Total Order Broadcast into a system that heavily resembles standard single-leader replication. However, it creates a chicken-and-egg problem: in order to safely elect that leader in the first place without risking a split-brain scenario, you must first use consensus.

### Living Without Consensus
Not every system requires consensus. Leaderless and multi-leader replication systems typically do not use global consensus. 

The write conflicts that occur in these systems are a direct consequence of skipping consensus. To successfully operate these systems, developers must accept that they need to cope without linearizability, and instead learn to work better with data that has branching and merging version histories.

## Breaking the Conundrum: Epochs & Quorums
To safely elect a leader without split-brain, consensus algorithms do not guarantee that the leader is universally unique at all times. Instead, they rely on a slightly weaker, but mathematically enforceable, guarantee.
### Strong vs. Weaker Leadership Guarantees
*   **The "Strong" Guarantee (Impossible):** This would demand that *there is only one leader existing in physical time.* This is impossible to enforce because network partitions can easily isolate a leader. That isolated leader will still think it is in charge, while the rest of the cluster safely elects a new one, creating a temporary overlap in physical time.
*   **The "Weaker" Guarantee (Practical):** This demands that *within a specific epoch (term/view), the leader is unique*. 

Every time an election happens, an epoch number (a monotonically increasing integer) is strictly incremented. If an old isolated leader wakes up and tries to issue a command (say, Epoch 4), but the rest of the cluster has already moved on to a new leader (Epoch 5), the cluster will reject the old leader's commands because `5 > 4`. The leader with the higher epoch always prevails.

### The Two-Round Voting Process
Before a leader can decide anything, it must prove it hasn't been ousted. 
1. Nodes vote to choose a leader.
2. Nodes vote on that leader's proposals.

If a quorum (majority) votes for a proposal, the leader knows it is still in charge, because it is guaranteed that at least one node in that majority would have alerted the leader if a higher epoch existed.

### Why Consensus Algorithms are Better than 2PC
While the voting looks similar, the differences are massive:
1.  **Quorum vs. Unanimity:** Consensus only needs a *majority* of "yes" votes. 2PC strictly requires a "yes" from *every single participant*.
2.  **Elected Leader:** 2PC has a hardcoded coordinator. Consensus algorithms dynamically elect theirs.
3.  **Automatic Recovery:** Consensus algorithms have built-in recovery processes to safely elect a new leader and sync states if a crash happens.

# Limitations of Consensus
Despite being a massive breakthrough for fault tolerance, consensus algorithms have severe costs:
*   **Synchronous Replication Penalty:** The proposal voting process is a form of synchronous replication, which hits performance heavily.
*   **Strict Quorum Waste:** To tolerate a single node failure, you must run and pay for three nodes.
*   **Static Memberships:** Most algorithms assume a fixed set of voting nodes. Dynamic membership changes are poorly understood and can be highly unreliable.
*   **Network Sensitivity:** Because they rely on timeouts to detect failure, highly variable network delays can trick the system into thinking the leader is dead. This causes the system to spend more time electing leaders than doing actual work.

# Membership and Coordination Services (ZooKeeper)

Services like ZooKeeper or etcd look like databases, but they are actually "coordination and configuration services" designed to hold very small amounts of metadata entirely in memory (with disk backups). 

Instead of writing complex consensus algorithms from scratch (which usually fails), developers "outsource" their consensus, failure detection, and ordering needs to ZooKeeper. 
### Core ZooKeeper Features & Their Ramifications
ZooKeeper provides a unique combination of features built on top of consensus that makes distributed system architecture much easier:
*   **Linearizable atomic operations:** You can use a compare-and-set operation to implement a distributed lock. 
    *   **Ramification:** If two nodes try to grab the same resource, only one succeeds, preventing race conditions.
*   **Total ordering of operations:** ZooKeeper gives every operation a monotonically increasing transaction ID (`zxid`). 
    *   **Ramification:** You can use these IDs as "fencing tokens." If a paused node wakes up late and tries to write to a database, the database can reject it because its token is older than the current lock holder's token.
*   **Failure detection (Ephemeral Nodes):** Clients maintain a heartbeat session with ZooKeeper. 
    *   **Ramification:** If a node crashes, its session times out, and ZooKeeper automatically deletes any locks (ephemeral nodes) that node was holding, preventing the system from freezing.
*   **Change notifications:** Clients can "watch" locks or values for changes. 
    *   **Ramification:** Nodes don't have to waste CPU and network bandwidth constantly polling for updates. They just wait for ZooKeeper to push an alert.

### Allocating Work to Nodes
*   The ZooKeeper/Chubby model is highly effective when you have multiple instances of a service and need to reliably choose one to act as the leader or primary.
*   It is also heavily used for partitioned resources (databases, message streams, etc.) to safely decide which partition is assigned to which node.
*   As nodes join or fail, ZooKeeper helps rebalance the load by safely moving partitions between existing nodes.
*   By using this model, you are **"outsourcing"** the complex work of coordinating nodes (consensus, operation ordering, and failure detection) to an external service.
*   **Limitation:** ZooKeeper is designed for slow-changing metadata (e.g., routing assignments that change every few minutes/hours). It is *not* intended for storing rapidly changing application runtime state.

### Membership Services (Internal Governance: The Roster)
*   **Who it's for:** The database nodes themselves.
*   **The Goal (The "Who"):** Determining exactly which nodes in the cluster are currently active and alive. 
*   **Why it requires consensus:** Network delays make it impossible for individual nodes to reliably guess if another node crashed. By coupling failure detection with consensus, the cluster forms a mathematically unified agreement on the exact roster of living members.
*   **Why it's mandatory:** You cannot run internal cluster operations (like electing a leader) if the nodes have divergent opinions on who is actually alive and eligible to vote. 

### Service Discovery (External Routing: The Endpoint)
*   **Who it's for:** External client applications (like your stateless web servers).
*   **The Goal (The "Where"):** Finding the specific IP address (or addresses) needed to connect to a service. 
*   **Piggybacking on Consensus (The Leader Use-Case):** While general service discovery might return a list of many web servers, in a single-leader database system, the client specifically needs to find the *one active leader* to write data. Since the Membership Service already used consensus to elect and track that leader, Service Discovery simply exposes that specific IP address to the external clients. 
*   **Scaling the lookups:** Client applications constantly ping for the leader's IP address. To prevent these read-heavy requests from bottlenecking the cluster's voting performance, consensus systems use **read-only caching replicas** to answer Service Discovery queries efficiently.

# Sidenote: The Equivalence of Consensus Problems
A wide range of complex problems in distributed systems are actually reducible to consensus and are entirely equivalent to each other. If you can solve one of these problems, you can easily transform that solution to solve any of the others. 

These equivalent problems all boil down to making a definitive *decision*:
*   **Linearizable compare-and-set registers:** The register must decide whether to set its value based on its current state.
*   **Atomic transaction commit:** The database must decide whether to commit or abort a distributed transaction.
*   **Total order broadcast:** The messaging system must decide the exact order in which to deliver messages.
*   **Locks and leases:** The lock must decide which competing client successfully acquired it.
*   **Membership/coordination service:** The system must decide which nodes are currently alive and which should be considered dead due to timeouts.
*   **Uniqueness constraint:** The constraint must decide which concurrent transaction to allow and which to reject when both try to create conflicting records with the same key.
